# Architecture Drivers

## 1. 목적

품질 시나리오 중 시스템 구조와 데이터 흐름에 큰 영향을 주는 요구를 선정한다. 이후 아키텍처 대안과 ADR은 이 문서를 기준으로 작성한다.

## 2. 기준 환경

- 회사 1,000개, 회사당 인스턴스 평균 20대
- 인스턴스는 1분마다 사용량 이벤트 발행
- 정상 초당 약 330건, 최대 초당 1,000건
- 성능 검증 데이터 1억 건
- 서로 다른 회사의 동시 사용자 500명

## 3. Architecture Drivers

### DR-01. 사용량과 금액의 정확성

중복, 지연, 순서 변경, 재처리가 발생해도 사용량과 금액이 달라지지 않아야 한다.

- 같은 이벤트는 한 번만 반영한다.
- 동일한 입력과 단가로 다시 계산하면 같은 결과가 나와야 한다.
- 월말 배치 결과와 스트리밍 집계 결과의 차이는 0원이어야 한다.
- 확정 금액의 사용량과 적용 단가를 추적할 수 있어야 한다.

### DR-02. 지속적인 이벤트 처리

이벤트가 계속 들어오거나 일시적으로 몰려도 유실 없이 처리해야 한다.

- 정상 초당 약 330건을 지속해서 처리한다.
- 초당 1,000건이 10분간 들어와도 유실하지 않는다.
- 처리 지연이 발생하면 복구 후 밀린 이벤트를 처리할 수 있어야 한다.

### DR-03. 빠른 월 누적 금액 조회

많은 이벤트가 저장된 상태에서도 최근 집계 기준의 월 누적 예상 금액을 빠르게 제공해야 한다.

- 동시 사용자 500명에서 응답시간 p95는 1초 이하여야 한다.
- 최신 데이터 반영은 최대 5분까지 늦을 수 있다.
- 응답에 집계 기준 시각을 포함해야 한다.

### DR-04. 실패 후 안전한 재처리

스트리밍 처리나 월말 배치가 중간에 실패해도 중복 없이 다시 처리할 수 있어야 한다.

- 실패 전까지의 처리 상태를 확인할 수 있어야 한다.
- 재실행 결과는 정상 실행 결과와 같아야 한다.
- 스트리밍 집계가 손상되어도 원본 사용량에서 다시 계산할 수 있어야 한다.

### DR-05. 회사별 데이터 분리

수집부터 조회까지 모든 단계에서 서로 다른 회사의 데이터가 섞이지 않아야 한다.

- 모든 사용량과 정산 결과는 회사 식별자를 가져야 한다.
- 다른 회사의 데이터를 요청하면 반환하지 않아야 한다.
- 집계와 캐시에서도 회사 구분이 유지되어야 한다.

## 4. 설계 우선순위

1. 정확성과 재처리 기준을 먼저 정한다.
2. 이벤트 처리와 저장 구조를 정한다.
3. 월 누적 금액 조회 구조를 정한다.
4. 모든 단계에서 회사별 데이터 분리를 검증한다.
