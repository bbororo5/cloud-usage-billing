# ADR-003: 실시간 비용 집계·조회 구조

## 상태

승인

## 배경

Kafka에 기록된 사용량 이벤트로 현재 월 예상 금액, 고정 대시보드와 조건이 달라지는 비용 탐색을 제공해야 한다. 예상 월간 원본은 약 8억 6,000만 건이며, 월간 배치 중에도 사용자 조회 성능을 유지해야 한다.

현재 집계 규모와 성능 한계를 측정하기 전에 별도 상태 처리 엔진을 도입하면 운영 구성과 복구 상태가 늘어난다. 이 결정에서는 가장 단순한 조회 구조를 기준선으로 선택하고, 선집계는 측정 결과가 요구할 때 추가한다.

## 요구사항

| 근거 | 요구사항 | 결정에 미치는 영향 |
|---|---|---|
| QS-01, DR-01 | 동일 `source + id`의 금액 반영은 한 번뿐이다. | 원본 중복을 제거한 후 집계해야 한다. |
| QS-02, DR-01 | 최대 10분 늦거나 순서가 바뀐 이벤트를 열린 월에 반영한다. | 이벤트 시간으로 조회 범위를 결정해야 한다. |
| QS-03, DR-02 | 평균 초당 330건, 최대 1,000건을 유실 없이 처리한다. | 적체 후 재적재할 수 있어야 한다. |
| QS-04, DR-03 | 1억 건에서 대시보드 조회 p95가 1초 이하다. | 고정 조회의 원본 집계 비용을 측정해야 한다. |
| QS-09, DR-03 | 월 누적 예상 금액의 지연은 5분 이하이며 기준 시각을 제공한다. | 적재 진행 상태를 결과와 함께 제공해야 한다. |
| QS-12, DR-03 | 월간 배치 중에도 조회 p95 1초를 유지하고 진행 중 결과를 노출하지 않는다. | 배치와 사용자 조회의 부하·결과를 격리해야 한다. |
| QS-13, DR-03 | 1억 건에서 비용 탐색 p95가 2초 이하다. | 기간·서비스·인스턴스별 분석 조회가 필요하다. |
| DR-05 | 모든 집계와 조회에 회사 범위를 유지한다. | 저장 키와 조회 조건에 회사 식별자가 필요하다. |

## 선택지

### A. 애플리케이션과 트랜잭션 DB 집계

```text
Kafka → 집계 애플리케이션 → 트랜잭션 DB → BFF
```

중복 제거와 집계를 DB 트랜잭션으로 묶기 쉽지만, 비용 탐색과 월간 배치를 위한 분석 저장소가 추가되어 조회 경로가 나뉜다.

### B. 상태 기반 스트림 처리 후 OLAP 조회

```text
Kafka → 스트림 처리 엔진 → OLAP 저장소 → BFF
```

중복 제거와 선집계를 지속적으로 수행해 조회 비용을 줄이지만, 별도 처리 상태와 복구·결과 적재를 운영해야 한다.

### C. OLAP 요청 시 집계

```text
Kafka → OLAP 저장소 → BFF 요청 시 중복 제거·집계
```

원본·비용 탐색·월간 배치의 저장소와 조회 경로를 통일한다. 반복 집계 비용과 배치 중 자원 경합은 성능 검증이 필요하다.

## 트레이드오프 분석

| 기준 | A. 트랜잭션 집계 | B. 스트림 처리 | C. OLAP 요청 시 집계 |
|---|---|---|---|
| 중복 정확성 | DB 유일성 제약 | 처리 상태에서 제거 | 조회 시 `source + id` 기준 제거 |
| 고정 조회 비용 | 낮음 | 낮음 | 원본 크기에 비례 |
| 동적 비용 탐색 | 별도 OLAP 필요 | OLAP에서 처리 | 같은 원본에서 처리 |
| 장애 복구 상태 | DB와 offset | offset·상태·결과 적재 | Kafka 적체와 OLAP 적재 |
| 운영 구성 | 두 조회 저장소 | 처리 엔진과 OLAP | Kafka와 OLAP |
| 확장 시점 | 처음부터 분리 | 처음부터 선집계 | 측정 후 선집계 추가 |

## 결정

ClickHouse에 원본 이벤트의 서비스별 사용량 레코드를 저장하고 요청 시 중복 제거 후 집계한다. 별도의 Kafka Streams 또는 선집계 처리 엔진은 두지 않는다.

- 원본은 `source + id` 기준으로 중복을 식별할 수 있게 저장한다.
- 후속 물리 모델은 사용량 전달 사본을 `MergeTree`에 보존하고 `argMax`로 중복을 제거한다. 작은 가격 사본만 `ReplacingMergeTree`와 `FINAL`을 사용한다.
- 대시보드, 비용 탐색과 원본 상세는 ClickHouse를 조회한다.
- BFF는 인증된 `tenantId`와 최대 31일 범위를 모든 조회에 강제한다.
- 마지막 적재 진행 시각을 조회 결과와 함께 제공한다.
- 월간 배치는 원본에서 다시 계산하고 완료된 결과만 공개한다.

Kafka에서 ClickHouse로 적재하는 방식과 테이블 정렬·파티션 키는 구현 전 후속 결정에서 정한다.

## 결과

- 원본 저장과 분석 조회 경로가 하나로 단순해진다.
- 처리 엔진의 상태 저장소와 복구 운영이 필요 없다.
- 고정 대시보드도 원본에서 집계하므로 반복 조회 비용이 발생한다.
- ClickHouse 적재·배치·조회가 자원을 공유하므로 동시 부하 테스트가 중요하다.
- QS-04, QS-12 또는 QS-13을 만족하지 못하면 선집계와 처리 엔진 도입을 새 ADR로 검토한다.
- ADR-001의 독립적인 현재 월 집계 프로세스 결정은 이 ADR로 대체한다. 현재 월 집계는 논리 책임으로 유지하되 별도 프로세스로 실행하지 않는다.
