# ADR-003: 실시간 비용 집계·조회 구조

## 상태

초안

## 배경

Kafka에 기록된 사용량 이벤트를 현재 월의 예상 금액으로 집계하고, BFF가 고정 대시보드와 조건이 달라지는 비용 탐색을 제공해야 한다. 이벤트 스트리밍과 논리적 책임 경계는 이미 확정했으며, 이 결정에서는 현재 월 집계와 조회 저장소를 구현하는 구조를 선택한다.

기술 제품을 먼저 정하지 않고, 집계 책임을 어디에 둘 것인지 두 구조를 비교한다.

## 요구사항

| 근거 | 요구사항 | 결정에 미치는 영향 |
|---|---|---|
| QS-01, DR-01 | 동일 `eventId`의 금액 반영은 한 번뿐이다. | 중복 제거와 집계 상태 변경의 일관성이 필요하다. |
| QS-02, DR-01 | 최대 10분 늦거나 순서가 바뀐 이벤트를 열린 월에 반영한다. | 이벤트 시간 기준의 보정이 필요하다. |
| QS-03, DR-02 | 평균 초당 330건, 최대 1,000건을 유실 없이 처리한다. | 적체 후 재처리와 병렬 처리가 가능해야 한다. |
| QS-04, DR-03 | 1억 건 기준 동시 사용자 500명의 조회 p95가 1초 이하다. | 원본이 아닌 조회용 집계 결과를 제공해야 한다. |
| QS-09, DR-03 | 월 누적 예상 금액의 지연은 5분 이하이며 기준 시각을 제공한다. | 집계 진행 상태를 결과와 함께 관리해야 한다. |
| QS-12, DR-03 | 월간 배치 중에도 조회 p95 1초를 유지하고 진행 중 결과를 노출하지 않는다. | 대량 배치와 사용자 조회의 부하·결과를 격리해야 한다. |
| QS-13, DR-03 | 1억 건에서 기간·서비스·인스턴스별 비용 탐색 p95가 2초 이하다. | 고정 선집계만으로 제한되지 않는 분석 조회가 필요하다. |
| DR-04 | 실패 후 중복 없이 다시 처리한다. | 처리 위치와 집계 상태를 복구할 수 있어야 한다. |
| DR-05 | 모든 집계와 조회에 회사 범위를 유지한다. | 집계 키와 조회 조건에 회사 식별자가 필요하다. |

집계 중단 중에도 마지막 정상 결과를 조회하며, 수집·집계 장애가 조회 기능 전체를 함께 중단시키지 않아야 한다.

## 선택지

### A. 트랜잭션 집계

```text
Kafka → 집계 애플리케이션 → 트랜잭션 DB → BFF
```

애플리케이션과 DB 트랜잭션이 중복 제거와 집계 갱신을 책임진다. 같은 DB가 조회용 집계 결과를 제공한다.

### B. 스트림 처리 집계

```text
Kafka → 상태 기반 스트림 처리 엔진 → 조회 저장소 → BFF
```

스트림 처리 엔진이 중복 제거, 상태 관리와 집계를 책임진다. 조회 저장소는 집계 결과 제공에 집중한다.

Kafka 수신·집계·조회를 하나의 데이터 플랫폼에 결합하는 구조는 확정한 실패 격리를 약화할 수 있어 이번 선택지에서 제외한다.

## 트레이드오프 분석

| 기준 | A. 트랜잭션 집계 | B. 스트림 처리 집계 |
|---|---|---|
| 중복 정합성 | DB 트랜잭션과 유일성 제약으로 통제 | 처리 상태와 결과 적재의 일관성 설계 필요 |
| 대량 이벤트 처리 | 이벤트에 비례해 DB 쓰기 증가 | 스트림에서 축약 후 조회 저장소에 반영 가능 |
| 장애 복구 | 처리 위치와 재처리를 직접 구현 | 상태 복구와 재처리를 처리 엔진이 지원 |
| 실패 격리 | 집계 애플리케이션과 DB 구성으로 분리 | 처리 엔진과 조회 저장소를 분리 |
| 구현·운영 | 초기 구조는 단순하나 배치 쓰기와 재처리 구현 필요 | 상태 저장과 복구 운영이 추가됨 |
| 검증할 역량 | 트랜잭션·인덱스·쿼리 최적화 | 상태 처리·복구·멱등한 결과 적재 |

## 결정 절차

1. 중복 제거와 장애 복구
2. 처리량과 조회 저장소 부하
3. 집계와 조회의 실패 격리
4. 구현·운영 복잡도

구조를 먼저 선택하고, 선택된 구조 안에서 기술 제품을 비교한다.

## 기술 스택 결정 범위

| 구조 | 결정할 기술 |
|---|---|
| A. 트랜잭션 집계 | Kafka Consumer 프레임워크, 트랜잭션 DB, 중복·처리 위치 관리 방식 |
| B. 스트림 처리 집계 | 스트림 처리 엔진, 상태·중복 관리 방식, 조회 저장소, 결과 적재 방식 |

파티션 수, 배치 크기와 인덱스 세부값은 구현·성능 테스트에서 정한다. 원본 사용량 원장과 월간 확정 배치 기술은 별도 ADR에서 결정한다.

## 결정

미정. 구조를 선택한 뒤 해당 구조 안에서 집계 엔진과 조회 저장소 제품을 비교한다.
