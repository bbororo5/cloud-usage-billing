# ADR-006: 테넌트·RBAC 강제 방식

## 상태

승인

## 배경

회사 1,000개의 사용량·정산 데이터를 공유 저장소에서 처리한다. 사용자 입력이나 쿼리 작성자의 주의에만 의존하면 테넌트 조건 누락이 다른 회사의 데이터 노출로 이어질 수 있다. Viewer와 Admin의 권한도 API 경로뿐 아니라 업무 진입점에서 일관되게 강제해야 한다.

## 요구사항

| 근거 | 요구사항 | 결정에 미치는 영향 |
|---|---|---|
| FR-08, FR-09 | 서버가 확인한 회사 범위를 전 과정에 유지한다. | 클라이언트의 `tenantId`를 신뢰하지 않는다. |
| QS-07, DR-05 | 다른 회사 데이터 노출은 0건이다. | 테넌트 없는 데이터 접근 경로를 제거한다. |
| QS-10, DR-06 | Viewer의 관리 요청을 거부한다. | 서비스 진입점에서 역할을 검사한다. |
| QS-11, FR-12 | 역할 변경을 즉시 반영하고 변경·거부를 기록한다. | 요청마다 현재 권한을 사용하고 보안 이력을 남긴다. |

## 선택지

### 데이터 격리

- 테넌트별 DB 또는 스키마
- 공유 테이블과 필수 `tenantId`

### 강제 위치

- 애플리케이션에서만 테넌트·역할 검사
- 애플리케이션을 주 경계로 두고 저장소에 가능한 방어를 중복 적용

### RBAC 진입점

- Controller 경로에서만 검사
- Spring Security Method Security로 서비스 진입점에서도 검사

## 트레이드오프 분석

| 기준 | 단순한 방식 | 선택한 방식과 비용 |
|---|---|---|
| 데이터 격리 | 테넌트별 DB는 격리가 강하다. | 공유 테이블은 적재·집계가 단순하지만 별도 강제 장치가 필요하다. |
| PostgreSQL | 애플리케이션 검사만 두면 구현이 쉽다. | RLS를 추가하면 실수를 차단하지만 요청별 DB 컨텍스트 관리가 필요하다. |
| ClickHouse | 쿼리마다 조건을 작성하면 간단하다. | 테넌트 스코프 조회 계층은 임의 SQL을 제한하지만 BFF가 신뢰 경계가 된다. |
| RBAC | Controller 검사는 눈에 잘 보인다. | 서비스 Method Security는 내부 호출도 방어하지만 프록시 기반 호출 규칙을 지켜야 한다. |

ClickHouse Row Policy를 테넌트마다 적용하려면 사용자·역할과 연결을 테넌트별로 관리해야 하므로 현재 범위에서는 사용하지 않는다.

## 결정

PostgreSQL과 ClickHouse는 공유 테이블을 사용하며 모든 테넌트 데이터에 `tenantId`를 필수로 저장한다. 이는 이벤트와 FOCUS 필드의 `BillingAccountId`와 같은 논리 식별자다.

- BFF는 현재 사용자 소속과 역할을 확인해 Spring Security의 `SecurityContext`를 구성한다.
- `SecurityContextHolder`의 ThreadLocal은 동기 사용자 요청에서만 사용한다.
- 서비스 진입점은 Method Security로 Viewer·Admin 역할을 검사한다.
- 인증 정보에서 만든 `TenantScope`를 데이터 접근 계층에 명시적으로 전달한다.
- 클라이언트가 보낸 `tenantId`는 데이터 범위 결정에 사용하지 않는다.
- PostgreSQL은 애플리케이션 검사와 RLS를 함께 적용한다. BFF 계정은 테이블 소유자와 `BYPASSRLS` 권한을 갖지 않는다.
- ClickHouse는 테넌트 없는 조회 API와 임의 SQL 접근을 제공하지 않는다. BFF는 읽기 전용 계정을 사용하고 수집·배치 계정과 분리한다.
- Kafka 처리는 이벤트의 `BillingAccountId`, 월간 배치는 작업의 `tenantId`를 명시적으로 사용하며 사용자 SecurityContext를 전파하지 않는다.
- 캐시 키와 실행·감사 기록에도 `tenantId`를 포함한다.

인증되지 않은 요청은 401, 자기 회사에서 역할이 부족한 요청은 403으로 응답한다. 다른 회사 리소스는 테넌트 범위 안에서 조회되지 않은 것으로 처리해 존재하지 않는 리소스와 동일하게 404로 응답한다.

## 결과

- 테넌트 조건을 개발자가 각 쿼리에 직접 기억하는 구조를 피한다.
- PostgreSQL은 애플리케이션 실수에도 RLS가 마지막 방어선이 된다.
- ClickHouse의 보안은 제한된 조회 계층과 BFF 읽기 전용 계정에 의존한다.
- 역할 검사는 Controller 외 호출에도 일관되게 적용된다.
- 테넌트 범위 없는 저장소 호출과 다른 회사 접근을 아키텍처·통합 테스트로 검증해야 한다.
- 역할 변경과 접근 거부 로그에는 사용자·회사·행위·판단·시각을 남기며 세션과 민감 데이터는 기록하지 않는다.
