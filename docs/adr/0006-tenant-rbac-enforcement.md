# ADR-006: 테넌트·RBAC 강제 방식

## 상태

승인

## 배경

회사 1,000개의 사용량·정산 데이터를 공유 저장소에서 처리한다. 사용자 입력이나 쿼리 작성자의 주의에만 의존하면 테넌트 조건 누락이 다른 회사의 데이터 노출로 이어질 수 있다. 데이터 접근 격리와 자원·장애 격리는 별개이며, 현재는 전자를 강제하고 후자는 확장 경로를 남긴다. Viewer와 Admin의 권한도 API 경로뿐 아니라 업무 진입점에서 일관되게 강제해야 한다.

## 요구사항

| 근거 | 요구사항 | 결정에 미치는 영향 |
|---|---|---|
| FR-08, FR-09 | 서버가 확인한 회사 범위를 전 과정에 유지한다. | 클라이언트의 `tenantId`를 신뢰하지 않는다. |
| QS-07, DR-05 | 다른 회사 데이터 노출은 0건이다. | 테넌트 없는 데이터 접근 경로를 제거한다. |
| QS-10, DR-06 | Viewer의 관리 요청을 거부한다. | 서비스 진입점에서 역할을 검사한다. |
| QS-11, FR-12 | 역할 변경을 즉시 반영하고 변경·거부를 기록한다. | 요청마다 현재 권한을 사용하고 보안 이력을 남긴다. |

## 선택지

### 데이터 격리

- 공유 테이블과 공용 DB 신원
- 공유 테이블과 테넌트별 DB 신원·Row Policy
- 테넌트별 DB 또는 테이블
- 셀 또는 테넌트별 전용 클러스터

### 강제 위치

- 애플리케이션에서만 테넌트·역할 검사
- 애플리케이션을 주 경계로 두고 저장소에 가능한 방어를 중복 적용

### RBAC 진입점

- Controller 경로에서만 검사
- Spring Security Method Security로 서비스 진입점에서도 검사

## 트레이드오프 분석

| 선택지 | 얻는 것 | 부담 |
|---|---|---|
| ClickHouse 공유 신원 | 계정 관리가 단순하다. | DB가 최종 테넌트를 구별하지 못해 애플리케이션 실수에 취약하다. |
| ClickHouse 테넌트별 신원 | 조건 누락도 Row Policy가 차단한다. | 계정·정책·자격증명 수명주기를 자동화해야 하며 자원 장애는 공유한다. |
| 테넌트별 DB·테이블 | 권한 경계가 명확하다. | 스키마 변경이 테넌트 수만큼 늘지만 자원 장애는 여전히 공유한다. |
| 셀·전용 클러스터 | 데이터와 장애 범위를 함께 격리한다. | 라우팅과 인프라 비용이 증가한다. |

PostgreSQL RLS는 요청별 DB 컨텍스트 관리 비용으로 애플리케이션 실수를 방어한다. Spring Method Security는 프록시 호출 규칙을 지켜야 하지만 Controller 밖의 서비스 진입점도 보호한다.

파티션과 샤딩은 데이터 배치 방식일 뿐 공용 권한의 교차 조회를 막지 못하므로 보안 경계로 사용하지 않는다.

## 결정

PostgreSQL과 ClickHouse는 공유 테이블을 사용한다. PostgreSQL의 비용·정산 데이터에는 `tenantId`를 필수로 저장한다. ClickHouse는 공유 테이블과 테넌트별 DB 신원·Row Policy를 사용한다.

- BFF는 현재 사용자 소속과 역할을 확인해 Spring Security의 `SecurityContext`를 구성한다.
- `SecurityContextHolder`의 ThreadLocal은 동기 사용자 요청에서만 사용한다.
- 서비스 진입점은 Method Security로 Viewer·Admin 역할을 검사한다.
- 인증 정보에서 만든 `TenantScope`를 데이터 접근 계층에 명시적으로 전달한다.
- 클라이언트가 보낸 `tenantId`는 데이터 범위 결정에 사용하지 않는다.
- PostgreSQL은 애플리케이션 검사와 RLS를 함께 적용한다. BFF 계정은 테이블 소유자와 `BYPASSRLS` 권한을 갖지 않는다.
- ClickHouse 원시 사용량은 회사 식별자를 갖지 않으며 수집·정산 프로세스만 접근한다.
- 점유 이력으로 회사 귀속을 확정한 조회 모델에 `billingAccountId`를 저장한다. 귀속 실패·중복은 공개하지 않고 오류로 격리한다.
- BFF는 원시 사용량을 읽지 못하며 귀속 조회 모델만 읽는다.
- BFF는 인증 세션의 회사를 테넌트별 ClickHouse 읽기 신원에 연결한다. 해당 신원의 Row Policy는 자기 회사 행만 허용한다.
- 테넌트별 계정·역할·정책·자격증명의 생성, 회전, 회수는 자동화한다. 회사마다 고정 연결 풀을 만들지는 않는다.
- 대형·고보안 고객은 향후 별도 셀이나 전용 클러스터로 이동할 수 있게 테넌트 라우팅 경계를 유지한다. 현재는 단일 셀만 구현한다.
- Kafka 처리는 VM `source`를 유지한다. 월간 배치는 작업의 `tenantId`와 사용 시점의 점유 이력을 명시적으로 사용하며 사용자 SecurityContext를 전파하지 않는다.
- 캐시 키와 실행·감사 기록에도 `tenantId`를 포함한다.

인증되지 않은 요청은 401, 자기 회사에서 역할이 부족한 요청은 403으로 응답한다. 다른 회사 리소스는 테넌트 범위 안에서 조회되지 않은 것으로 처리해 존재하지 않는 리소스와 동일하게 404로 응답한다.

## 결과

- 테넌트 조건을 개발자가 각 쿼리에 직접 기억하는 구조를 피한다.
- PostgreSQL은 애플리케이션 실수에도 RLS가 마지막 방어선이 된다.
- ClickHouse는 원시 접근 차단과 귀속 조회 모델로 노출 경로를 제한한다.
- 테넌트별 DB 신원과 Row Policy가 누락된 회사 조건을 차단한다. BFF의 잘못된 DB 신원 선택은 별도 테스트와 감사 대상이다.
- 단일 셀에서는 CPU·메모리·장애 범위를 공유한다. 실제 요구가 생기면 셀 단위로 물리 분리한다.
- 역할 검사는 Controller 외 호출에도 일관되게 적용된다.
- 테넌트 범위 없는 저장소 호출과 다른 회사 접근을 아키텍처·통합 테스트로 검증해야 한다.
- 역할 변경과 접근 거부 로그에는 사용자·회사·행위·판단·시각을 남기며 세션과 민감 데이터는 기록하지 않는다.
