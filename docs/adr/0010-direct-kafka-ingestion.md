# ADR-010: 사용량 발생기의 Kafka 직접 발행

## 상태

승인 — 코드 전환 전. ADR-001·002·007·008의 접수 API 경유 및 Kafka 기록 전 검증을 변경한다.

직접 발행 결정은 유지한다. 아래의 독립 원장 적재기 배치는 이후 ClickHouse 직접 소비 목표로 변경 검증 중이며, [구현 로드맵](../implementation-roadmap.md)에서 추적한다.

## 배경

프로젝트가 발생기를 통제하므로 HTTP 접수 서버를 별도로 운영할 이점이 작다. 발생기가 Kafka에 직접 발행하고 기존 원장 적재기가 검증을 맡아 실행 단위를 줄인다. API 제거가 전체 시스템의 단일 장애점을 없앤다는 의미는 아니다.

## 요구사항

- 내구성 있는 수신과 at-least-once 재처리를 유지한다.
- 잘못된 이벤트는 과금 원장에 반영하지 않는다.
- 인증된 발생기와 VM 출처의 연결을 검증하고 회사 정보는 입력에 넣지 않는다.

## 선택지

- HTTP 접수 API에서 인증·검증 후 Kafka 발행
- 발생기가 Kafka에 직접 발행하고 소비 단계에서 검증·격리

## 트레이드오프 분석

| 선택지 | 이점 | 부담 |
|---|---|---|
| 접수 API | 연결·검증 중앙화, 발생기의 Kafka 의존 제거 | 서버 운영·추가 경유·인증 DB 의존 |
| 직접 발행 | 접수 서버와 해당 동기 DB 의존 제거 | 발생기의 Kafka 연결·인증·재시도 관리, 소비 단계 검증과 격리 필요 |

## 결정

- 발생기는 회사·가격을 모르는 Kafka producer로 동작한다. key는 VM `source`, 동일 이벤트 재시도 시 `source + id`를 유지한다.
- Kafka 내구성 ACK는 수신 완료이며 계약 검증 완료를 의미하지 않는다. HTTP 접수 API는 목표 실행 구성에서 제거한다.
- 기존 `usage-ledger-writer`가 계약·출처 검증 후 유효 레코드만 ClickHouse에 적재한다. 별도 검증 프로세스는 추가하지 않는다.
- 잘못된 이벤트는 식별 정보·사유를 내구성 있게 격리한 뒤 소비를 진행한다. 적재·격리 실패 시 offset을 진행하지 않는다.
- 브로커 인증·쓰기 권한을 적용한다. payload의 `source`나 Kafka key만으로 발행자 신원을 신뢰하지 않는다. 신원과 출처를 검증 가능하게 연결하는 구체적 방법은 구현 전에 정한다.

## 결과

접수 API는 없어지지만 검증·보안 책임은 유지된다. 브로커 ACL만으로 payload 출처 검증이 완성됐다고 보지 않는다. 현재 로컬 PLAINTEXT 구성은 개발용이며 운영 보안 완료를 뜻하지 않는다.

발생기 직접 발행, 안전한 출처 연결, 검증 실패 격리, 격리 실패 후 재처리를 구현·검증한 뒤 기존 API 코드를 제거한다. C2는 목표 구조를 표시한다.
