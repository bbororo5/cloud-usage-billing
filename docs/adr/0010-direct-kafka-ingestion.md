# ADR-010: 사용량 발생기의 Kafka 직접 발행

## 상태

승인 — 직접 발행·내장 소비로 코드 전환. 구현 결과·미검증 범위는 [수집 구현·검증](../ingestion-implementation.md)을 따른다. 2026-09-13 보완으로 운영자 통제 입력을 신뢰하고 별도 내용·출처 검증과 자동 격리를 제외한다. ADR-001·002·007·008의 이전 수집 경로를 변경한다.

## 배경

발생기는 클라우드 운영자가 통제하며 고객은 측정 설정·출처·발행 자격증명을 변경할 수 없다. 입력의 정확성을 발생기 계약으로 두고, 파이프라인은 내구성 있는 전달·저장과 중복 반영 방어에 집중한다. 최초 접수 API·독립 적재기 및 소비 단계 검증안은 이 결정으로 대체한다.

## 요구사항

- 입력은 회사·가격을 모르는 원시 사용량이다.
- 발생기가 계약에 맞는 출처·측정값을 생성하고 재전송 시 같은 식별자와 내용을 유지한다.
- at-least-once 재전달에도 사용량·비용은 한 번만 반영한다.
- 저장 실패로 이벤트를 유실하지 않으며, 회사 귀속·조회 권한 검증은 유지한다.

## 선택지

- 접수 API 또는 중간 처리 서버에서 내용·출처 검증 후 적재
- 운영자 통제 입력을 신뢰하고 Kafka → ClickHouse 직접 소비

## 트레이드오프 분석

| 선택지 | 이점 | 부담 |
|---|---|---|
| 별도 검증 계층 | 입력 오류 분류·격리와 복구를 명시하기 쉽다. | 실행 단위와 오류 처리 상태가 늘고 출처 증명도 별도로 필요하다. |
| 신뢰 입력·직접 소비 | 내용 검증·자동 격리 계층 없이 전달·저장·멱등성에 집중한다. | 잘못된 측정값이나 침해된 발생기의 사칭을 수집 단계에서 탐지·차단한다고 보장하지 않는다. 계약 위반으로 소비가 중단될 수도 있다. |

공유 토픽은 VM별 토픽·권한 관리를 줄인다. 토픽 ACL은 허용된 발행자의 접근만 제한하며 메시지의 source를 증명하지 않는다.

저장 완료는 단순 쓰기 성공 대신 디스크 동기화 완료로 잡는다. offset 진행 후 OS 미기록 데이터가 사라지는 위험을 줄이는 대신, 동기화 대기에 따른 처리량·지연 비용을 부담한다.

## 결정

- VM은 측정 대상이고 발생기는 고객이 변경할 수 없는 운영자 관리 프로그램이다. 실제 측정 인프라는 구현하지 않고 발생기로 모사한다.
- 모든 VM의 사용량은 공유 토픽 하나에 발행한다. key는 source이며 점유 제어는 별도 토픽을 유지한다.
- 발생기는 내구성 ACK를 받기 전까지 미확인 이벤트를 보존·재전송한다. 동일 이벤트의 식별자는 source + id, 서비스별 레코드는 source + id + meter다.
- 기본 경로는 발생기 → Kafka → ClickHouse다. ClickHouse는 파싱 후 사용량 배열을 유지한 이벤트당 1행을 저장한다. 일반 뷰에서 이벤트 단위 중복 제거 후 필요 시 서비스별로 펼친다. 별도 내용·출처 검증과 자동 오류 격리는 도입하지 않는다. 저장 단위의 비교 근거는 [물리 모델](../clickhouse-physical-data-model.md#저장-단위의-선택과-트레이드오프)을 따른다.
- 물리적으로 중복 저장될 수 있지만 귀속·조회·월간 계산에서는 같은 논리 레코드를 한 번만 반영한다. 입력의 동일 식별자·동일 내용은 발생기 계약으로 신뢰한다.
- 파싱·저장 불가는 처리 실패로 남기고 조용히 건너뛰지 않는다. 적재 묶음의 데이터·파일 메타데이터 디스크 동기화가 완료된 뒤 해당 offset을 진행한다. 그 전에 실패하면 복구 후 재처리한다.
- 중단 후 같은 consumer group의 파티션별 committed offset에서 재개한다. 일시 장애는 간격을 두고 재시도하고 지속 실패는 알린다. 재시도 소진으로 폐기·건너뛰지 않으며, 보관 만료 전 적체 경고·대응을 둔다. 세부 수치는 구현 전 정한다.
- 브로커 인증·쓰기 권한은 유지한다. 향후 더 강한 출처 격리·내용 검증이 필요하거나 직접 소비의 복구 요구를 충족하기 어렵다면 중간 처리 서버를 재검토하고 승인받는다.

## 결과

수집 단계의 입력 검증 범위를 의도적으로 줄인다. 이는 입력을 신뢰한다는 프로젝트 전제이지 입력 정확성의 기술적 증명이 아니다. 회사 귀속 오류 격리·가격 검증·테넌트 및 RBAC 방어는 변경하지 않는다.

직접 소비의 적재 내구성·중복 결과 불변·실패 복구는 구현 전 검증한다. 기존 API·적재기 코드는 전환 전 기반이며, 새 경로 검증 후 정리한다.

건너뛰지 않는 복구 정책은 유실을 피하는 대신 지속 장애·잘못된 입력으로 소비가 막히는 비용이 있다. Kafka 보관 기간은 유한하므로 재시도만으로 무기한 복구를 보장하지 않는다.

디스크 자체의 영구 손실까지 이 완료 기준으로 보장하지 않는다. 구체 설정과 장애 실험은 [저장소 계약](../storage-access-contract.md#3-이벤트-적재)·[테스트 계획](../architecture-test-plan.md)을 따른다.
