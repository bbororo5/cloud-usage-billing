# ADR-004: 월간 검증·확정 배치

## 상태

승인

## 배경

현재 월 예상 금액은 빠른 조회를 위한 잠정값이다. 월 마감 후에는 ClickHouse의 원본 이벤트에서 다시 계산하고 검증한 금액만 확정해야 한다. 배치 실패가 사용자 조회와 기존 확정 결과에 영향을 주어서는 안 된다.

## 요구사항

| 근거 | 요구사항 | 결정에 미치는 영향 |
|---|---|---|
| FR-05, QS-05 | 실패한 배치를 중복 없이 재실행한다. | 실행 상태와 실패 지점을 기록해야 한다. |
| QS-06, DR-01 | 같은 원본과 가격으로 같은 결과를 만든다. | 원본에서 결정적으로 다시 계산해야 한다. |
| QS-07, DR-05 | 회사 간 정산 데이터를 격리한다. | 처리와 확정의 기본 단위를 테넌트로 둔다. |
| QS-12, DR-03 | 배치 중에도 조회 성능과 기존 결과를 유지한다. | 작업 부하와 진행 중 결과를 사용자 조회에서 격리해야 한다. |
| DR-04 | 실패 후 안전하게 복구한다. | 부분 결과를 확정하지 않고 실패 범위만 재처리해야 한다. |

## 선택지

### 실행 주체

- ClickHouse 내부 SQL 작업이 집계와 실행을 모두 담당한다.
- Java 배치가 실행을 관리하고 ClickHouse가 대량 집계를 수행한다.

### 처리 단위

- 모든 테넌트의 한 달을 한 작업으로 처리한다.
- 테넌트별로 집계·검증하고 실패한 테넌트만 재처리한다.

### 결과 관리

- 같은 월의 확정 결과를 실행 버전별로 관리한다.
- 검증 완료 후 월간 확정 결과를 한 번만 저장한다.

## 트레이드오프 분석

| 결정 | 단순한 선택 | 선택한 방식과 비용 |
|---|---|---|
| 실행 주체 | ClickHouse 내부 작업은 빠르게 도입할 수 있다. | Java 배치는 구성요소가 늘지만 단계·실패·재시도를 명시하고 테스트할 수 있다. |
| 처리 단위 | 월 전체 작업은 상태가 단순하다. | 테넌트 분할은 작업 수가 늘지만 부하를 조절하고 실패 범위를 줄인다. |
| 결과 관리 | 실행 버전은 재정산 이력을 보존한다. | 한 번만 확정하면 단순하지만 확정 후 금액을 수정할 수 없다. |

## 결정

Java 배치가 실행을 지휘하고 ClickHouse가 원본 스캔과 집계 SQL을 수행한다. Java가 원본 이벤트를 건별로 계산하지 않는다.

- `tenantId + billingMonth`를 기본 처리 단위로 삼는다.
- 대형 테넌트의 기간 분할은 측정 결과가 필요할 때 추가한다.
- 실행별 `runId`와 상태를 기록하고 실패한 테넌트만 재시도한다.
- 월 마감 후 2시간의 유예를 두고 UTC 02:00에 배치를 시작한다.
- 시작 전 이벤트 적체와 ClickHouse 적재 지연이 해소됐는지 확인하며, 남아 있으면 확정을 연기한다.
- 중간 결과는 공개하지 않고 검증에 성공한 월간 결과만 한 번 저장한다.
- 확정 후 이전 월 이벤트는 격리하고 재정산하지 않는다.

## 결과

- 배치 절차와 장애 복구 책임이 Java 코드에 드러난다.
- ClickHouse의 대량 집계 성능을 사용하면서 원본의 애플리케이션 반출을 피한다.
- 한 테넌트의 실패가 다른 테넌트의 계산과 확정을 막지 않는다.
- 실행 이력은 남지만 확정 결과의 다중 버전과 재정산은 지원하지 않는다.
- Java 배치와 실행 상태 저장소를 운영해야 한다.
