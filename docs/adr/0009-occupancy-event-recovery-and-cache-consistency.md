# ADR-009: 점유 변경의 Kafka 기반 복구와 캐시 일관성

## 상태

승인 — 2026-09-23 경계 보완, 2026-09-24 기획 위임으로 공개 확인 계약 추가. 구현·장애 검증 전

변경 이력: 이전의 내부 시작 요청·활성화·재할당 차단은 외부 인프라 책임으로 옮겼다. Kafka 기반 사실 복구·캐시 버전·공개 보류 결정은 유지한다. 아래는 보완된 결정이며 과거 선택의 새 점유 가용성 비용은 더 이상 내부 책임이 아니다.

## 배경

외부 인프라가 확정한 VM 점유 시작·종료에 따라 회사 귀속이 달라진다. 내부는 VM을 제어하지 않고 이력을 반영한다. 캐시로 반복 조회를 줄이되 오래된 이력으로 타사 사용량을 공개하면 안 되며, 원장·캐시 부분 반영도 복구해야 한다.

## 요구사항

- 사용 시점의 점유 회사에만 데이터를 공개한다. (FR-09, DR-05)
- 점유 변경을 잃지 않고 중복 재처리에도 같은 결과를 유지한다.
- VM 제어와 외부 사실의 내부 반영을 구분한다. 사실 이벤트는 요청 만료로 폐기하지 않는다. [요구사항](../requirements.md), [처리 계약](../storage-access-contract.md#점유-사실의-수신과-반영-완료)

## 선택지

- 이력 조회: PostgreSQL 직접 묶음 조회 / PostgreSQL 원장과 캐시 / ClickHouse 이력 사본
- 변경 복구: 사실 수신 후 원장·캐시 직접 갱신 / Kafka 기록 후 재처리
- 반영 지연: 기존 캐시로 계속 처리 / 영향 구간 공개 보류
- 미도착 사실 확인: 일정 시간 대기·DB 재조회 / 외부 발행자의 이력 전달 완료 확인

## 트레이드오프 분석

| 선택 | 얻는 것 | 부담·선택 근거 |
|---|---|---|
| PostgreSQL 직접 조회 | 사본 갱신 불필요 | 묶음 조회로 호출을 줄여도 같은 이력을 반복해서 읽는다. |
| PostgreSQL 원장과 캐시 | 반복 읽기를 줄이고 누락 시 원장 조회 | 갱신·버전 관리와 공개 안전성 확인이 필요하다. 성능 효과는 측정한다. |
| ClickHouse 이력 사본 | 사용량과 DB 내부 조인 가능 | 사본 동기화·완전성 관리가 필요해 채택하지 않는다. 캐시 역시 사본이라는 부담은 남는다. |
| 직접 갱신 | 처리 경로가 짧음 | 부분 성공 후 전달이 끝나면 별도 복구 기록이 필요하다. |
| Kafka 기록 후 재처리 | 기존 인프라로 변경 사실 보존·복구 | 중복·순서·보관 기간 관리가 필요하다. 장애 복구 근거를 남기기 위해 선택한다. |
| 반영 확인 전 공개 보류 | 오래된 이력의 오귀속 방지 | 영향 구간의 데이터 최신성을 양보한다. 외부 재할당은 막지 않으므로 미도착 사실을 포함한 공개 확인 계약이 필요하다. |
| 일정 시간 대기·DB 재조회 | 추가 입력 계약이 없음 | 지연된 변경의 부재를 증명하지 못해 회사 격리의 근거로 사용할 수 없다. |
| 외부의 이력 전달 완료 확인 | 사용 구간까지 필요한 사실이 반영됐는지 판단 가능 | 외부에 누락 없는 확인·연속 번호 계약이 추가된다. 확인이 늦으면 공개도 늦어진다. 격리를 최신성보다 우선해 선택한다. |

## 결정

- PostgreSQL을 점유 이력 원장으로 두고 캐시를 사용한다. 과거 이력이 없으면 원장을 조회한다.
- 외부가 확정한 점유 사실은 사용량과 별도 Kafka 토픽에 VM source를 key로 기록한다. 내부 VM 제어 명령은 다루지 않는다.
- 원장·캐시를 멱등하게 갱신하고 결과를 내구 기록한 뒤 offset을 commit한다. 부분 실패는 재처리한다.
- VM별 버전으로 오래된 캐시 갱신을 거부한다. 늦은 사용량 이벤트는 버리지 않고 과거 점유 이력으로 귀속한다.
- 반영 안전성 확인 전 영향 구간 공개를 보류한다. 이미 읽은 캐시를 사용하는 처리에도 적용하며 외부 재할당은 차단하지 않는다.
- 외부 발행자의 VM별 이력 전달 완료 확인과 연속 번호를 사용한다. 내부는 이력·확인 범위의 동일 버전 반영 후 해당 범위만 공개한다. 사용량 스키마는 유지하며 [연결 계약](../occupancy-attribution-contract.md)에 정상·대기·정정 조건을 둔다.

## 결과

읽기 비용을 줄이는 대신 변경 경로에 일관성 관리가 추가된다. Kafka ACK는 변경 기록의 보존이며 원장·캐시 반영 완료를 뜻하지 않는다.

외부 확인은 신뢰 계약이며 Kafka가 대신 보장하지 않는다. 정확한 입력 스키마·발행 번호 보존·캐시 기술·공개 경합·재시작 복구는 후속 LLD에서 정한다. 캐시 갱신 ACK만으로 미도착 점유 사실의 부재를 보장하지 않는다. [테스트 계획](../architecture-test-plan.md)의 점유 캐시·과거 귀속·점유 사실 지연·종료 반영 복구로 검증한다.
