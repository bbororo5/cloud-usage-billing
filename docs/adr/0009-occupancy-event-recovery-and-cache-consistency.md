# ADR-009: 점유 변경의 Kafka 기반 복구와 캐시 일관성

## 상태

승인 — 구현·장애 검증 전

## 배경

공유 VM의 점유 시작·종료에 따라 회사 귀속이 달라진다. 반복되는 점유 이력 조회는 캐시로 줄일 수 있지만, 오래된 이력으로 다른 회사에 사용량을 공개하면 안 된다. 원장과 캐시 중 하나만 갱신된 장애도 복구해야 한다.

## 요구사항

- 사용 시점의 점유 회사에만 데이터를 공개한다. (FR-09, DR-05)
- 점유 변경을 잃지 않고 중복 재처리에도 같은 결과를 유지한다.
- 요청 만료와 실제 종료 사실을 구분한다. [요구사항](../requirements.md), [처리 계약](../storage-access-contract.md#점유-요청-기한과-완료-조건)

## 선택지

- 이력 조회: PostgreSQL 직접 묶음 조회 / PostgreSQL 원장과 캐시 / ClickHouse 이력 사본
- 변경 복구: 요청에서 원장·캐시 직접 갱신 / Kafka 기록 후 재처리
- 반영 지연: 기존 캐시로 계속 처리 / 영향 구간 공개와 새 점유 활성화 보류

## 트레이드오프 분석

| 선택 | 얻는 것 | 부담·선택 근거 |
|---|---|---|
| PostgreSQL 직접 조회 | 사본 갱신 불필요 | 묶음 조회로 호출을 줄여도 같은 이력을 반복해서 읽는다. |
| PostgreSQL 원장과 캐시 | 반복 읽기를 줄이고 누락 시 원장 조회 | 갱신·버전 관리가 필요하다. 변경 시 갱신과 활성화 확인을 결합하는 조건으로 선택한다. 성능 효과는 측정한다. |
| ClickHouse 이력 사본 | 사용량과 DB 내부 조인 가능 | 사본 동기화·완전성 관리가 필요해 채택하지 않는다. 캐시 역시 사본이라는 부담은 남는다. |
| 직접 갱신 | 처리 경로가 짧음 | 부분 성공 후 요청이 사라지면 별도 복구 기록이 필요하다. |
| Kafka 기록 후 재처리 | 기존 인프라로 변경 사실 보존·복구 | 중복·순서·보관 기간 관리가 필요하다. 장애 복구 근거를 남기기 위해 선택한다. |
| 반영 확인 전 보류 | 오래된 이력의 오귀속 방지 | 장애 시 새 점유 가용성과 데이터 최신성을 양보한다. |

## 결정

- PostgreSQL을 점유 이력 원장으로 두고 캐시를 사용한다. 과거 이력이 없으면 원장을 조회한다.
- 점유 제어 메시지는 사용량과 별도 Kafka 토픽에 VM source를 key로 기록한다.
- 원장·캐시를 멱등하게 갱신하고 결과를 내구 기록한 뒤 offset을 commit한다. 부분 실패는 재처리한다.
- VM별 버전으로 오래된 캐시 갱신을 거부한다. 늦은 사용량 이벤트는 버리지 않고 과거 점유 이력으로 귀속한다.
- 반영 확인 전 새 점유 활성화와 영향 구간 공개를 보류한다. 이미 읽은 캐시를 사용하는 처리에도 적용한다.

## 결과

읽기 비용을 줄이는 대신 변경 경로에 일관성 관리가 추가된다. Kafka ACK는 변경 기록의 보존이며 원장·캐시 반영 완료를 뜻하지 않는다.

캐시 기술, 원자적 버전 비교·활성화 판정, 공개 보류의 재시작 복구는 후속 구현 설계에서 정한다. [테스트 계획](../architecture-test-plan.md)의 점유 캐시·과거 귀속·요청 만료·종료 복구로 검증한다.
