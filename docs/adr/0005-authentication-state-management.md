# ADR-005: 인증 상태 관리

## 상태

승인

## 배경

등록된 사용자는 웹 대시보드에서 BFF만 호출한다. 로그아웃·계정 차단·역할 제거는 기존 인증 상태에도 즉시 반영해야 한다. 외부 클라이언트와 독립 API에 사용자 토큰을 전달하는 요구는 없다.

## 요구사항

| 근거 | 요구사항 | 결정에 미치는 영향 |
|---|---|---|
| FR-10 | 로그인 상태를 유지하고 로그아웃할 수 있다. | 인증 상태의 생성·만료·폐기가 필요하다. |
| FR-08, FR-09 | 회사와 역할은 서버가 확인한 정보로 결정한다. | 클라이언트의 회사·역할 정보를 신뢰하지 않는다. |
| QS-11, DR-06 | 역할 제거를 기존 인증 상태에 즉시 반영한다. | 중앙에서 인증 상태를 확인하고 폐기할 수 있어야 한다. |
| DR-06 | 인증 상태를 확인할 수 없으면 기본 차단한다. | 인증 저장소 장애 시 요청을 허용하지 않는다. |

## 선택지

### 인증 상태

- 서버 세션과 공유 세션 저장소
- Access·Refresh JWT와 공유 denylist 저장소

### 공유 세션 저장소

- PostgreSQL 기반 Spring Session JDBC
- Redis 기반 Spring Session

## 트레이드오프 분석

### 인증 상태

| 기준 | 서버 세션 | JWT와 denylist |
|---|---|---|
| 요청 검증 | 공유 세션 조회 | 서명 검증 후 denylist 조회 |
| 즉시 폐기 | 세션 삭제 | Access·Refresh Token 폐기 |
| 권한 최신성 | 서버의 현재 역할 확인 | claim을 쓰지 않거나 별도 상태 확인 |
| 운영 요소 | 세션 만료·저장소 | 토큰 회전·재사용 탐지·서명 키·denylist |
| 분산 검증 | 공유 저장소 의존 | denylist 때문에 공유 저장소 의존 |

JWT도 요구사항을 만족할 수 있지만 즉시 폐기를 위해 중앙 조회가 다시 필요하다. 현재 구조에서는 분산 검증 이점 없이 토큰 생명주기와 키 관리가 추가된다.

### 공유 세션 저장소

| 기준 | PostgreSQL | Redis |
|---|---|---|
| 도입 비용 | 기존 사용자·권한 DB 재사용 | 별도 저장소 운영 |
| 조회·만료 | 인덱스 조회와 만료 정리 작업 | 인메모리 조회와 TTL |
| 부하 격리 | 사용자·권한 데이터와 자원 공유 | 세션 부하를 분리 |
| 현재 적합성 | 동시 사용자 500명 기준선 | 세션 부하가 병목일 때 유리 |

현재도 권한 확인에 PostgreSQL이 필요하므로 Redis만 추가해 인증 경로의 PostgreSQL 의존성을 제거할 수 없다.

## 결정

불투명한 서버 세션과 PostgreSQL 기반 Spring Session JDBC를 사용한다.

- 브라우저 쿠키에는 무작위 세션 ID만 저장한다.
- 쿠키에 `HttpOnly`, `Secure`, `SameSite=Strict`를 적용한다.
- 세션은 사용자 식별만 담당하고 회사와 역할은 서버의 현재 데이터에서 확인한다.
- 로그인 성공 시 세션 ID를 교체한다.
- 로그아웃·계정 차단·역할 변경 시 관련 세션을 폐기한다.
- 인증 또는 권한 저장소 장애 시 기본 차단한다.
- 상태 변경 요청에는 CSRF 방어를 적용한다.
- 비활동 30분 만료를 적용하며 별도 절대 만료는 두지 않는다. 서버 시각이 마지막 접근+30분 이상이면 거부하고, 유효 세션으로 인증된 요청 시작 시 접근을 갱신한다.
- 유효한 인증 세션의 재로그인은 `409`로 거부하고 기존 신원·세션 ID를 유지한다. 계정 변경은 로그아웃 후 로그인한다.
- 세션 검증을 마친 진행 중 요청은 로그아웃으로 취소하지 않으며 인가·공개 검사는 계속한다. 폐기 완료 후 검사하는 요청은 거부하고, 늦은 저장으로 폐기 세션을 복원하지 않는다.
- PostgreSQL 인증 작업을 끝내고 커넥션을 반환한 뒤 ClickHouse를 조회한다.

위 생명주기 보완은 2026-10-01 승인했다. 쿠키 이름은 [OpenAPI](../../contracts/openapi.yaml)의 `SESSION`을 따른다. 정책의 실제 프레임워크 강제 여부는 BFF 구현 단계에서 검증한다.

## 결과

- 인증 상태와 권한 변경을 중앙에서 즉시 통제할 수 있다.
- BFF는 로컬 세션을 갖지 않아 수평 확장할 수 있다.
- PostgreSQL에 세션 조회·갱신·만료 정리 부하가 추가된다.
- 인증 단계 p95와 커넥션 대기를 부하 테스트로 측정한다.
- 세션 부하가 PostgreSQL 병목으로 확인되면 Redis 분리를 재검토한다.
- 외부 클라이언트나 독립 API의 분산 검증이 필요해지면 JWT를 재검토한다.
