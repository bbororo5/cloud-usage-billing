# ADR-002: 실시간 비용 집계를 위한 이벤트 스트리밍

## 상태

승인

## 배경

인스턴스는 1분마다 사용량 이벤트를 발행하고, 시스템은 이를 월초부터 현재까지의 예상 금액으로 집계한다. 이벤트 접수와 실시간 집계는 ADR-001에 따라 독립 프로세스로 실행한다.

집계 프로세스가 중단되더라도 접수한 이벤트를 잃거나 발생기의 전송을 계속 막아서는 안 된다. 이벤트를 먼저 복구 가능한 곳에 기록하고, 집계는 자신의 처리 위치부터 다시 읽을 수 있어야 한다. 따라서 프로세스 사이의 전달 수단은 단순 통신이 아니라 적체와 재생을 책임지는 영속 경계다.

이 결정에서는 그 영속 경계의 구현과 전달·순서·중복 처리 원칙을 정한다.

## 요구사항

| 근거 | 요구사항 | 결정에 미치는 영향 |
|---|---|---|
| FR-01, DR-02 | 이벤트를 지속적으로 수신한다. | 집계 중단과 이벤트 접수를 격리해야 한다. |
| QS-01, DR-01 | 동일 이벤트의 중복 반영은 0건이다. | 중복 전달을 허용하되 결과를 멱등하게 만든다. |
| QS-02 | 최대 10분 지연·순서 변경 이벤트를 보정한다. | 이벤트 시간을 보존하고 늦은 이벤트도 전달·재생해야 한다. |
| QS-03 | 초당 1,000건을 10분간 유실 없이 처리한다. | 적체를 내구성 있게 보존해야 한다. |
| QS-09, DR-03 | 예상 금액의 데이터 지연은 5분 이하다. | 집계 소비 지연을 측정하고 제한해야 한다. |
| DR-04 | 실패 후 원본에서 중복 없이 다시 처리한다. | 소비 위치 기반 재처리가 가능해야 한다. |
| FR-09, DR-05 | 전 과정에서 회사 식별자를 유지한다. | 이벤트와 파티션 키에 회사 범위를 포함한다. |

## 선택지

- DB Outbox
- Apache Kafka
- Apache Pulsar

## 트레이드오프 분석

| 요구 | DB Outbox | Apache Kafka | Apache Pulsar |
|---|---|---|---|
| 수신 이벤트 유실 방지 | 원본과 Outbox를 DB에 커밋 | 복제된 파티션 로그에 커밋 | BookKeeper에 영속 기록 |
| 집계 중단 중 접수 | Outbox 적체가 원장 DB와 자원 공유 | 로그에 적체되어 접수와 집계 격리 | BookKeeper에 적체되어 격리 |
| 실패 후 재생 | 상태·순번 기반 재조회를 구현 | Consumer Group의 offset을 이동 | Subscription의 cursor를 이동 |
| 중복 반영 방지 | DB 저장은 유일성 제약, 전달은 중복 가능 | 외부 DB 반영 시 중복 가능 | 외부 DB 반영 시 중복 가능 |
| 5분 이내 반영 | 폴링 주기와 DB 부하를 조정 | 소비 지연을 측정·축소 | 구독 지연을 측정·축소 |
| 로컬 재현 | 기존 DB 활용, 큐 처리 로직 구현 | Kafka 클러스터 실행 | Broker·BookKeeper·Metadata Store 실행 |

### DB Outbox

원본과 전달 의무를 한 트랜잭션으로 확정할 수 있다. 그러나 집계 중단으로 생긴 적체가 원장 DB에 쌓이고, 소비 위치와 재생을 직접 구현해야 한다. 이 시스템은 기존 DB 변경을 외부로 전달하는 것이 아니라 외부 이벤트를 지속적으로 받으므로 Outbox의 원자성보다 적체 격리와 재생이 더 중요하다.

### Apache Kafka

복제 로그가 접수와 집계를 분리하고, 소비자는 offset부터 다시 처리한다. 외부 DB 반영과 하나의 트랜잭션을 만들 수 없어 중복 처리가 필요하지만, 이는 At-least-once와 `eventId` 기반 멱등 처리 원칙으로 통제한다. 접수 지속, 적체 보존, 독립 재생 요구를 직접 만족한다.

### Apache Pulsar

Kafka와 마찬가지로 영속 적체와 재생 요구를 만족한다. 그러나 현재 요구에는 메시지 서빙과 저장의 독립 확장이 필요하지 않아 추가 구성요소를 운영할 근거가 없다.

유실을 허용하는 At-most-once는 과금 정확성 요구를 만족하지 않아 제외한다. End-to-end Exactly-once는 보장하지 않고 멱등한 처리 결과를 만든다.

## 결정

Apache Kafka를 영속 메시지 로그로 사용한다.

- 검증된 이벤트를 복제된 Kafka 로그에 기록한 후 수신 성공을 반환한다.
- 기록에 실패하면 성공을 반환하지 않고 발생기가 재시도한다.
- 전달 방식은 At-least-once로 한다.
- 중복 반영은 `eventId` 기반 멱등 처리로 방지한다.
- 파티션 키는 `tenantId + instanceId`를 사용한다.
- 순서는 같은 인스턴스의 이벤트에 대해서만 보장한다.
- 후속 처리마다 독립적인 소비 위치를 사용한다.
- 보관 기간은 허용 가능한 최대 복구 시간보다 길게 설정한다.

파티션 수와 복제 설정의 구체적인 값은 부하 테스트와 실행 환경에 맞춰 정한다.

## 결과

- 집계 중단 중에도 이벤트를 계속 보존할 수 있다.
- 소비자는 저장된 위치부터 독립적으로 재처리할 수 있다.
- 같은 인스턴스의 이벤트 순서와 병렬 처리를 함께 확보한다.
- 중복 전달을 정상 상황으로 취급하고 모든 금액 반영을 멱등하게 구현해야 한다.
- Kafka 장애 시 이벤트 접수는 실패하며 발생기가 재시도해야 한다.
- Kafka 클러스터 운영과 소비 지연 감시가 필요하다.
