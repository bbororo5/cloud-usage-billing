# BFF 접근 통제 테스트 설계

## 1. 범위·판정 방법

LLD ③의 설계 문서다. **자동 테스트 구현·실행 결과가 아니다.** [책임·계약](bff-access-lld.md), [API](api-contract.md), [인증 ADR](adr/0005-authentication-state-management.md), [인가 ADR](adr/0006-tenant-rbac-enforcement.md)를 기준으로 한다. 가격 계산·월간 배치 자체·부하 검증은 제외한다.

```text
입력 + 서버 상태 + 의존 저장소 상태
 → 인증 → 인가 → 공개 가능성
 → 응답 + 저장 상태 + 금지된 후속 동작의 부재
```

각 ID는 하나의 검증 목적이며 표 안의 구분은 매개변수 사례로 펼친다. 정상 기준에서 한 조건씩 바꾸고, 권한·회사·승인처럼 함께 결과를 결정하는 조건은 조합을 명시한다. 기대값은 구현 함수가 아닌 고정 사용자·회사·역할·귀속표에서 만든다. 모든 요청을 거부하는 구현도 탈락하도록 양성 대조군을 둔다.

| 실행 범위 | 용도 |
|---|---|
| 규칙·계약 | 고정 기대표, 입력 제약, 결과 매핑, 구조 의존 검사. 프레임워크 내부를 재구현하지 않음 |
| 보안 통합 | 실제 Spring 필터·Method Security 프록시·Spring Session JDBC·일회용 PG. HTTP 클라이언트로 쿠키를 따로 보관 |
| 조회 연결 | 보안 통합 + 실제 CH·실제 BFF DB 신원. 서비스 직접 호출만으로 HTTP·DB 격리 검증을 대체하지 않음 |

거부 시 상태 코드뿐 아니라 보호된 업무 핸들러/저장소 호출·응답 내용·DB 변경을 관측한다. 인증/인가 근거 조회까지 금지하는 것은 아니다. 저장소 오류 대역은 응답 매핑에만 쓰고, 실제 자격증명·권한·연결 장애 검사를 별도로 둔다. 경합은 latch/barrier로 순서를 고정하고 임의 sleep으로 재현하지 않는다.

## 2. 인증

### 입력·상태 분해

- 입력: 자격 증명 정상/불일치/스키마 위반, 쿠키 없음/미등록 ID/기존 ID, CSRF 정상/누락/불일치.
- 상태: 사용자 없음/활성/차단, 세션 없음/미인증/인증됨/만료/폐기, 로그인 전후·로그아웃 전후.
- 환경: 세션·사용자 조회 정상/실패, 세션 저장·폐기 성공/실패. 음성 사례에서는 다른 보안 조건을 정상으로 맞춰 원인을 분리한다.

| ID | 경우·전이 | 독립 오라클 | 최소 범위 |
|---|---|---|---|
| A01 | 올바른 자격 증명 + 활성 사용자 | 로그인 후 새 요청에서 기대 사용자 ID 확인. 로그인 응답만으로 통과하지 않음 | 보안 통합 |
| A02 | 틀린 비밀번호×활성/차단, 맞는 비밀번호+차단, 사용자 없음 | `401`, 새 인증 상태 없음, 후속 보호 요청도 미인증. 대외 오류 코드·본문 형태는 동일하며 계정 존재·차단 여부 비노출 | 보안 통합 |
| A03 | 필수 필드 누락·빈 비밀번호·이메일 형식 위반 | 유효 CSRF 상태에서 스키마/API에 맞는 입력 오류, 새 인증 상태 없음. 파서 오류·내부 정보 비노출 | 계약 + 보안 통합 |
| A04 | 보호 요청의 쿠키 없음/미등록/폐기/유효 | 앞 세 경우 `401`·업무 진입 없음, 유효 쿠키만 기대 사용자로 진입. 클라이언트 사용자 ID로 대체 금지 | 보안 통합 |
| A05 | 미인증 S1 → 로그인 → 인증 S2 | S1≠S2, S2는 기대 사용자로 동작, S1은 보호 요청 `401`. 저장소에 세션이 있다는 사실만으로 인증 성공 판정 금지 | 실제 HTTP 서버 포함 보안 통합 |
| A06 | 로그인 → 보호 요청 성공 → 로그아웃 완료 → 옛 쿠키 재사용 | 완료 뒤 시작한 요청 `401`, 새 요청에서도 서버의 폐기 효과 유지. 쿠키 삭제만 관측하지 않음 | 보안 통합 |
| A07 | 만료 직전/정확한 경계/직후, 유효 요청 후 갱신 | 선택한 만료 정책의 고정 시각표와 비교. 만료 청소 작업 전에도 인증 거부해야 함. 정확한 경계는 G1 결정 후 고정 | 시간 통제 검사 + 실제 저장소 통합 |
| A08 | 세션·사용자 조회 실패, 인증 상태 저장 실패 | `503`·업무 진입 없음·허위 로그인 성공 없음. 복구 후 정상 로그인 가능한 양성 대조. 성공 응답 유실과 저장 실패를 구분 | 보안 통합·실제 의존 장애 |
| A09 | 로그아웃 중 세션 폐기 저장 실패 | 완료를 거짓 보고하지 않고 `503`. 복구 후 재시도·옛 쿠키 거부 확인. 실패 응답만으로 모든 세션이 폐기됐다고 주장하지 않음 | 보안 통합 |
| A10 | 상태 변경 요청의 CSRF 정상/누락/불일치 | 정상 대조는 실행, 누락/불일치는 `403`·로그인/로그아웃/역할 변경 동작 없음. 공격 문자열·비밀 비노출 | 보안 통합 |
| A11 | 세션 쿠키·인증 실패 응답·로그 | HTTPS의 `HttpOnly`·`Secure`·`SameSite=Strict`, 세션 ID/비밀번호가 URL·오류·로그에 없음. 실제 브라우저 쿠키 전송은 웹 연결 단계에서 별도 검증 | HTTP 헤더·로그 검사 |
| A12 | BFF 인스턴스 1 로그인 → 2 조회·로그아웃 → 1 재조회 | 공유 PG에서 동일 신원 확인 후 옛 세션 거부. 인스턴스 로컬 인증 상태에 의존하지 않음 | 보안 통합·두 애플리케이션 컨텍스트 |

### 인증 정책 관문 — 승인 전 기대값을 임의 확정하지 않음

- **G1 만료:** 비활동/절대 만료 여부·기간·정확한 비교 경계·갱신 기준을 정해야 A07의 기대 시각을 고정할 수 있다. 실제 저장 정밀도에 맞는 직전/직후 값을 쓰고 긴 sleep으로 만료를 기다리지 않는다.
- **G2 재로그인:** 기존 API는 인증된 사용자의 로그인도 허용한다. 성공 시 신원·새 세션 ID 확인은 유지하되, 실패 후 기존 인증 유지/폐기 및 다른 계정 전환 정책은 미결이다. 결정 후 기존 A 세션→B 로그인 성공/실패 전후의 신원·쿠키를 비교한다.
- **G3 진행 중 요청:** 폐기 완료 후 시작한 요청은 반드시 거부한다. 이미 인증된 요청은 완료 허용/취소 중 선택해야 한다. ‘인증 완료에서 정지→로그아웃 완료→재개’ 순서로 선택한 결과를 검증한다. 계정 차단·역할 제거에 자동으로 같은 정책을 적용하지 않는다.

인증 `503` 등 합의한 오류가 OpenAPI에 빠진 부분은 계약 동기화와 예제 검사 대상이다. 이 문서가 자동 계약 검사를 대신하지 않는다.

## 3. 인가

축은 **신원·현재 소속 / 현재 역할 / 요청 행위 / 대상 회사 / 변경 시점**이다. A·B 회사에 Viewer·Admin·역할 없는 사용자를 고정하고 같은 역할·같은 형태의 자원을 둔다. 역할이 충분하다는 사실과 대상 회사가 같다는 사실을 독립적으로 검사한다.

| ID | 경우·전이 | 독립 오라클 | 최소 범위 |
|---|---|---|---|
| Z01 | Viewer/Admin × 비용·정산·사용량 조회/구성원 조회/역할 변경·제거 | API 권한표를 손으로 고정. 둘 다 비용 조회 허용, 관리 행위는 Admin만 허용. 거부는 `403`·업무 실행/변경 없음 | 권한표 + 실제 Method Security 프록시 |
| Z02 | 인증 없음, 활성 소속 없음, 역할 없음 | 인증 없음은 `401`, 신원은 확인됐지만 소속/권한이 없으면 `403`. 실제 차단 후 세션이 폐기됐다면 다음 요청 `401`도 구분 | 보안 통합 |
| Z03 | 허용 역할 + 자기 회사/타사/존재하지 않는 대상 | 자기 회사 양성 대조. 타사 단건과 없는 단건은 동일 `404` 의미·본문 형태, 목록은 타사 행·수·식별자 비노출. 고유 traceId 값은 비교에서 제외 | 조회 연결 |
| Z04 | 요청의 가짜 userId·tenantId·역할, 컨텍스트와 전달 신원 불일치 | 인증된 신원과 현재 소속만 사용. 거부하거나 계약상 무시하더라도 타사 범위로 바뀌지 않음. 범위 없는 데이터 접근은 차단 | 보안 통합 + 구조 검사 |
| Z05 | Controller 대신 서비스 진입점 호출 | 실제 보안 프록시를 통해 Viewer의 관리 호출 거부, Admin의 자기 회사 호출 허용. 보호를 우회하는 자기 호출/다른 업무 진입점이 없는지 구조 검사 | Spring 컨텍스트 + 구조 검사 |
| Z06 | Admin→Viewer/역할 제거/계정 차단 완료 뒤 옛 세션 재사용 | ADR대로 관련 세션 폐기, 다음 요청 차단. 재로그인 가능한 경우 현재 권한만 적용. 세션에 과거 역할을 남겨 권한 유지 금지 | 보안 통합 |
| Z07 | 현재 소속·역할 조회 실패 | `503`, 과거 권한·기본 회사·전체 회사로 대체 금지, 업무 실행 없음. 복구 후 허용 대조 | 보안 통합·의존 장애 |
| Z08 | 마지막 Admin 제거, 두 Admin의 동시 상호 제거 | 마지막 Admin 제거는 `409`, DB에 Admin 최소 한 명 유지. 두 변경을 barrier로 겹쳐 불변식 위반 커밋이 없는지 검사 | 실제 PG·업무 진입점 |
| Z09 | A→B 순차 요청·동시 요청·예외 후 같은 스레드/연결 재사용 | 응답·업무 범위·감사 기록의 회사가 각각 일치. ThreadLocal·DB 컨텍스트 잔류 없음. 비동기 경로가 생기면 같은 오라클 적용 | 보안 통합·풀 크기 제한 |
| Z10 | 역할 변경 허용·거부 | 사용자·회사·행위·판단·시각이 감사에 남고 비밀번호·세션 값은 없음. 거부된 변경은 DB에 반영되지 않음 | 보안 통합·DB/로그 관측 |

**G4 권한 변경 경합:** 변경 완료 뒤 시작하는 요청의 현재 권한 적용은 확정이다. 검사 통과 후 진행 중인 업무에 대한 차단 시점은 미결이다. ‘권한 검사 완료→역할 제거 완료→업무 재개’를 통제해 선택한 정책을 검사한다. G3 로그아웃 정책으로 대체하지 않는다.

## 4. 공개 가능성

축은 **요청 회사 / 승인 개정 / 현재 이력·차단 범위 / CH 저장 결과 / 조회 순서·장애**다. 승인 정보를 BFF가 생성하거나 워커를 동기 호출하는 테스트는 만들지 않는다. 실제 BFF 역할에는 필요한 읽기만 허용해야 한다.

고정 원장: A 승인 이벤트 E1의 개정 R1과 미승인 R2, B 승인 E2, A 귀속 오류로 차단된 E3, 회사 미확정 E4를 준비한다. E1의 현재 VM 점유자는 B여도 당시 귀속 회사는 A다. 기대 회사·이벤트·개정·세 측정값은 별도 고정표로 작성한다.

| ID | 경우·전이 | 독립 오라클 | 최소 범위 |
|---|---|---|---|
| P01 | A/B의 정상 승인 조회, 과거 사용량 | A는 E1/R1만, B는 E2만 조회. 현재 점유자로 바꾸지 않음. 최신 번호 R2를 선택하지 않고 고정 측정값과 일치 | 조회 연결 |
| P02 | 미승인·준비 중·폐기 개정, 확인 부족·귀속 오류 | 해당 결과의 내용 비공개. 회사 미확정 E4를 추정 귀속하지 않음. 직접 CH에 준비 결과를 넣어도 고객 조회로 승격되지 않음 | 조회 연결 |
| P03 | 승인 후 관련 이력 오류, 다른 VM·관련 없는 구간 | 해당 범위 비공개, 독립된 안전 범위의 조회는 계속 성공. 차단 구간 시작/종료와 사용 구간의 겹침은 고정 구간표로 판정 | 구간 규칙 + 조회 연결 |
| P04 | 동일 개정 중복 저장, 다른 내용의 동일 개정, 승인 개정 누락 | 같은 내용은 논리 결과 한 번·측정값 불변. 충돌/누락은 판단 불가, 임의 행·미승인 개정·빈 결과로 대체 금지 | 실제 PG·CH |
| P05 | PG 승인/차단 조회 실패, CH 읽기 실패 | 데이터 반환 없이 장애 처리. 정상 빈 조회와 구분하며 0원·빈 목록 성공으로 위장 금지. 부분 응답을 이미 전송한 뒤 오류로 바꾸는 경로 금지 | 조회 연결·단계별 장애 주입 |
| P06 | 회사 필터 누락·BFF의 잘못된 CH 신원 선택 | 실제 A 읽기 신원은 필터 없이도 B 행 접근 불가. BFF 라우팅에 잘못된 신원을 주입하면 A 응답에 B 데이터 없음. 공용 신원 우회 금지 | 실제 CH Row Policy + BFF 연결 |
| P07 | 실제 BFF PG 계정으로 범위 누락·타사 지정·연결 재사용 | RLS/권한으로 허용 밖 데이터 접근 거부. 소유자·BYPASSRLS 계정으로 검증하지 않음. BFF의 원시 CH·준비 테이블 직접 접근도 거부 | 실제 양 DB 실행 계정 |
| P08 | 승인·차단 조회 직후 오류 발생, 결과 읽기 중 오류 발생 | 아래 G5의 두 실행 순서에서 허용된 결과만 관측. 단순 ‘PG 먼저, CH 나중’ 성공 사례만으로 통과하지 않음 | 실제 PG·CH·동기화 지점 |
| P09 | 정상 결과+차단 결과가 섞인 목록 | 차단 데이터 비공개, 안전한 범위는 독립 조회 가능, 불완전한 값을 완전한 총계로 표시 금지. 한 요청의 부분/전체 보류 응답은 G6 확정 후 고정 | 조회 연결 |
| P10 | 타사/변조 커서, 다음 페이지 전에 역할·차단 변경 | 기존 커서가 최신 접근·차단 검사를 우회하지 않음. 타사 데이터·내부 식별 정보 비노출. 정상 페이지는 API의 고정 조회 기준·정렬 유지 | 계약 + 조회 연결 |
| P11 | BFF 재시작 후 같은 신원·조회 조건 | 승인·차단·회사 범위와 논리 결과 유지. 로컬 메모리의 과거 승인으로 공개 금지 | 별도 프로세스 조회 연결 |

### 공개 경합·응답의 설계 관문

- **G5 공개와 차단의 선후관계:** (a) 차단이 먼저 확정되면 진행 중 조회도 해당 결과를 공개하면 안 된다. (b) 안전한 조회가 먼저 완료되도록 보호한다면 차단 확정은 그 뒤에 일어나야 한다. 이미 전달한 응답을 회수할 수 있다고 가정하지 않는다. 공개 완료의 논리적 기준점과 두 DB 사이에서 이를 강제할 수단은 ④에서 제시하고 테스트 지점으로 연결한다.
- 기존 [저장소 계약](storage-access-contract.md)은 CH 호출 전에 PG 연결 반환을 요구하지만, [워커 내부 조회](usage-attribution-implementation.md)는 결과 읽기 동안 PG 잠금을 유지한다. **BFF가 내부 조회를 그대로 복사하거나 단순 버전 재조회로 해결했다고 간주하지 않는다.** G5를 만족하는 구조가 확인되기 전 고객 읽기 권한을 열지 않는다. 기존 연결 계약 변경은 별도 검토한다.
- **G6 부분 결과:** 부분 반환이면 공개 가능한 행과 불완전 상태를 구분하고, 전체 보류이면 정상 독립 요청까지 차단하지 않는다. 어느 쪽도 차단된 타사/회사 미확정 데이터의 존재·개수·내용을 알려주면 안 된다. 선택 후 구체 응답 스키마·오류 코드와 고정 예제를 API 계약에 반영한다.

월간 확정액 자체의 계산·확정 경합, 조회/월/가격 경계 배분은 다음 모듈의 오라클 대상이다. 배치 실패를 정상 귀속 데이터 전체 차단으로 바꾸지 않는다.
