# Logical Architecture

## 1. 목적

기술과 배포 방식을 정하기 전에 시스템의 책임, 데이터 소유권, 흐름과 의존 관계를 정의한다.

## 2. 시스템 경계

### 내부

- 사용량 수집·집계와 비용 계산
- 월간 검증·확정
- 인증·권한 관리와 BFF
- 웹 대시보드

### 외부

- 사용량 이벤트 발생기
- 실제 클라우드와 결제 시스템
- 외부 인증 제공자
- Admin·Viewer 사용자

이벤트 발생기는 운영 경계 밖에 두되 재현과 부하 검증을 위해 저장소에 포함한다.

## 3. 책임과 데이터 소유권

| 책임 경계 | 역할 | 소유 데이터 |
|---|---|---|
| 이벤트 접수 | 이벤트 검증·거부 | 거부 이벤트와 사유 |
| 사용량 원장 | 유효 이벤트 보존·중복 판정 | 유효 사용량 원본 |
| 비용 계산 규칙 | 가격 선택·금액 계산 | 가격표와 가격 버전 |
| 현재 월 집계 | 요청 시 예상 금액 계산 | 영속 소유 데이터 없음 |
| 월간 정산 | 재계산·비교·확정 | 실행 상태, 차이, 확정 금액 |
| 비용 조회 | 예상·확정·비용 탐색 결과 제공 | 조회 캐시만 선택적으로 소유 |
| 사용자·접근 통제 | 인증·회사·역할 관리 | 사용자, 회사 소속, 역할 |
| 웹 대시보드 | 비용과 권한 관리 화면 제공 | 임시 화면 상태 |

## 4. 핵심 데이터 흐름

### 현재 월 예상 금액

```text
이벤트 발생기 → 이벤트 접수 → 사용량 원장
→ 비용 계산 규칙 → 현재 월 집계 → 비용 조회 → 웹 대시보드
```

### 월간 확정 금액

```text
사용량 원장 → 비용 계산 규칙 → 월간 정산
→ 비용 조회 → 웹 대시보드
```

현재 월 집계는 월간 정산의 비교 대상일 뿐 원본이 아니다.

Kafka에서 ClickHouse로 원장을 적재하는 책임은 이벤트 접수와 분리된 `usage-ledger-writer`가 실행한다. 현재 월 집계는 ClickHouse 요청 시 계산이므로 별도 실행 단위가 아니다.

### 인증과 권한 관리

```text
웹 대시보드 → 사용자·접근 통제
→ 인증된 회사와 역할로 조회 또는 구성원 관리
```

## 5. 의존 원칙

- 사용량 원장만 유효 사용량 원본을 변경한다.
- 현재 월 집계와 월간 정산은 같은 계산 규칙을 사용한다.
- 비용 조회는 사용량 원장과 예상·확정 결과를 변경하지 않는다.
- 월간 정산은 진행 중 결과를 공개하지 않고 비용 조회의 응답시간을 침해하지 않는다.
- 웹 대시보드는 저장소에 직접 접근하지 않는다.
- 모든 과금 데이터는 회사 식별자를 유지한다.
- 논리 경계와 배포 단위는 동일하지 않을 수 있다.

## 6. 실패 책임

| 상황 | 책임과 복구 원칙 |
|---|---|
| 이벤트 이상 | 접수는 오류를 격리하고, 원장은 중복을 한 번만 반영하며, 현재 월 집계는 지연 이벤트로 열린 월을 보정한다. |
| ClickHouse 적재 중단 | Kafka 접수는 계속하고 이미 적재된 원장으로 조회하며 `dataAsOf`로 지연을 드러낸다. 복구 후 offset부터 다시 적재한다. |
| 월간 정산 실패 | 부분 결과를 공개하지 않고 실패를 기록하며, 기존 확정 금액을 유지한 채 안전하게 재실행한다. |
| 인증·권한 실패 | 기본 차단하며 다른 회사 데이터의 존재 여부도 노출하지 않는다. |

발생기에서 전송되지 않은 이벤트의 탐지는 제외하되, 수신한 유효 이벤트의 내부 유실은 허용하지 않는다.

## 7. 멀티테넌시·RBAC 원칙

- 역할은 사용자와 회사의 소속 관계에 부여한다.
- 회사와 역할은 서버가 확인한 인증 정보에서 가져온다.
- 사용자 요청에 회사 범위 없는 데이터 접근을 허용하지 않는다.
- 비동기·배치 처리와 캐시도 회사 범위를 유지한다.
- Viewer는 조회만, Admin은 자기 회사의 구성원 권한만 관리한다.
- 역할 변경은 기존 접근 권한에 반영하고 변경·거부 이력을 기록한다.

세부 기술은 ADR에서 결정한다.
