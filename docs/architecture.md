# Logical Architecture

## 1. 목적

기술과 배포 방식을 정하기 전에 시스템의 책임, 데이터 소유권, 흐름과 의존 관계를 정의한다.

## 2. 시스템 경계

### 내부

- 사용량 수집·집계와 비용 계산
- 월간 검증·확정
- 인증·권한 관리와 BFF
- 웹 대시보드

### 외부

- 사용량 이벤트 발생기
- 실제 클라우드와 결제 시스템
- 외부 인증 제공자
- Admin·Viewer 사용자

이벤트 발생기는 운영 경계 밖에 두되 재현과 부하 검증을 위해 저장소에 포함한다.

## 3. 책임과 데이터 소유권

| 책임 경계 | 역할 | 소유 데이터 |
|---|---|---|
| 이벤트 수신 로그 | 운영자 관리 발생기의 이벤트 내구 보존 | Kafka 전달 로그 |
| 원장 적재 | 신뢰한 이벤트의 파싱·이벤트 단위 저장, 실패 재처리 | 영속 소유 데이터 없음 |
| 원시 사용량 원장 | 원시 이벤트 보존·중복 반영 방어 (테넌트 비인지) | 원시 사용량 원본 |
| 사용량 귀속 | 사용 시점의 회사–VM 점유 관계 확인 및 귀속 모델 생성 | 회사–VM 점유 이력, 귀속 조회 모델 |
| 귀속 오류 격리 | 미귀속·중복 점유 데이터 격리 및 확정 차단 | 귀속 오류 이력 |
| 비용 계산 규칙 | 가격 선택·금액 계산 | 가격표와 가격 버전 |
| 현재 월 집계 | 요청 시 예상 금액 계산 | 영속 소유 데이터 없음 |
| 월간 정산 | 재계산·비교·확정 (미귀속 검증) | 실행 상태, 차이, 확정 금액 |
| 비용 조회 | 예상·확정·비용 탐색 결과 제공 (BFF) | 조회 캐시만 선택적으로 소유 |
| 사용자·접근 통제 | 인증·회사·역할 관리 | 사용자, 회사 소속, 역할 |
| 웹 대시보드 | 비용과 권한 관리 화면 제공 | 임시 화면 상태 |

## 4. 핵심 데이터 흐름

### 현재 월 예상 금액

```text
이벤트 발생기 → Kafka → 이벤트 단위 적재 → 원시 사용량 원장
→ 사용량 귀속(점유 이력) → 귀속 조회 모델 → 비용 계산 규칙 → 현재 월 집계 → 비용 조회(BFF) → 웹 대시보드
```

### 월간 확정 금액

```text
원시 사용량 원장 + 사용량 귀속(점유 이력) [미귀속 0건 검증]
→ 비용 계산 규칙 → 월간 정산 → 비용 조회(BFF) → 웹 대시보드
```

현재 월 집계는 월간 정산의 비교 대상일 뿐 원본이 아니다.

원장은 사용량 배열을 유지하고 이벤트 단위로 중복 제거한 뒤 필요한 처리에서 서비스별로 펼친다. 사용자 조회 모델의 물리 형태는 별도로 확정한다.

현재 경로는 발생기 → Kafka → ClickHouse 직접 소비다. 입력은 운영자 통제 발생기의 계약으로 신뢰하며 별도 접수 API·적재기·내용 검증·자동 격리는 두지 않는다. 로컬 적재·멱등성·복구 검증과 미검증 범위는 [수집 구현·검증](ingestion-implementation.md), 전체 진행은 [구현 로드맵](implementation-roadmap.md), 컨테이너 관계는 [C2](diagrams/c2-containers.svg)를 따른다. 현재 월 집계는 요청 시 계산하며 별도 실행 단위가 아니다.

### 인증과 권한 관리

```text
웹 대시보드 → 사용자·접근 통제
→ 인증된 회사와 역할로 조회 또는 구성원 관리
```

## 5. 의존 원칙

사용량은 공유 토픽 하나를 사용한다. 향후 더 강한 입력 검증·출처 격리가 필요하거나 직접 소비의 복구 요구를 충족하기 어려우면 중간 처리 서버를 재검토한다. 세부 조건은 [ADR-010](adr/0010-direct-kafka-ingestion.md)을 따른다.

- 원시 사용량 원장만 원시 사용량 원본을 기록한다.
- 현재 월 집계와 월간 정산은 같은 계산 규칙을 사용한다.
- 비용 조회 및 BFF는 원시 사용량 원장에 접근하지 못하며, 귀속 완료된 조회 모델만 읽는다.
- 비용 조회는 사용량 원장과 예상·확정 결과를 변경하지 않는다.
- 월간 정산은 진행 중 결과를 공개하지 않고 비용 조회의 응답시간을 침해하지 않는다.
- 웹 대시보드는 저장소에 직접 접근하지 않는다.
- 원시 사용량은 VM 출처를 유지하고, 비용·정산 데이터는 사용 시점의 회사 식별자를 유지한다.
- 논리 경계와 배포 단위는 동일하지 않을 수 있다.

코드 수준에서는 실행 모듈끼리의 의존, 공용 라이브러리의 실행 모듈 의존, 제품 코드의 테스트 모듈 의존을 금지한다. 공용 라이브러리 사용과 테스트 코드의 제품 참조는 허용한다. 이는 데이터 교환이나 DB 조회 금지가 아니다. [검사 범위](../tests/module-boundaries/README.md)는 Gradle의 Java `main` 프로젝트 의존이며 내부 패키지 계층은 아직 고정하지 않는다.

## 6. 실패 책임

| 상황 | 책임과 복구 원칙 |
|---|---|
| 중복·지연 이벤트 | 계산은 중복을 한 번만 반영하고 열린 월은 지연 사용량으로 보정한다. 내용 오류의 자동 탐지·격리는 현재 수집 범위 밖이다. |
| 파싱·저장 실패 | 소비 실패로 남기고 건너뛰지 않는다. 원인 해소 후 재처리한다. |
| ClickHouse 적재 중단 | Kafka 보관·용량 한도 내에서 접수를 계속하고, 조회가 가능한 경우 마지막 귀속 완료 데이터로 응답한다. 저장소 자체 장애는 오류로 응답한다. 복구 후 offset부터 다시 적재한다. |
| 미귀속·중복 점유 이상 | 오류로 격리하고 해결 전 관련 월간 확정을 차단한다. 귀속 회사를 모르는 오류의 차단 범위는 후속 설계한다. |
| 월간 정산 실패 | 부분 결과를 공개하지 않고 실패를 기록하며, 기존 확정 금액을 유지한 채 안전하게 재실행한다. |
| 인증·권한 실패 | 기본 차단하며 다른 회사 데이터의 존재 여부도 노출하지 않는다. |

발생기에서 전송되지 않은 이벤트의 탐지는 제외하되, 수신한 유효 이벤트의 내부 유실은 허용하지 않는다.

## 7. 멀티테넌시·RBAC 원칙

- 역할은 사용자와 회사의 소속 관계에 부여한다.
- 회사와 역할은 서버가 확인한 인증 정보에서 가져온다.
- 사용자 요청에 회사 범위 없는 데이터 접근을 허용하지 않는다.
- ClickHouse는 테넌트별 읽기 신원과 Row Policy로 저장소 차원의 데이터 격리를 강제한다.
- 비동기·배치 처리와 캐시도 회사 범위를 유지한다.
- Viewer는 조회만, Admin은 자기 회사의 구성원 권한만 관리한다.
- 역할 변경은 기존 접근 권한에 반영하고 변경·거부 이력을 기록한다.

세부 기술은 ADR에서 결정한다.
