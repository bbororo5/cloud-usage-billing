# ClickHouse Physical Data Model

> 상태: 2026-09-16 이벤트 단위 원장·일반 뷰 승인, 구현 전. 현재 SQL은 서비스별 행을 저장하는 이전 기반이다. ClickHouse 직접 소비와 귀속 조회 모델도 구현·검증 전이며, 아래 표는 구현 상태를 보증하지 않는다.

## 1. 목적

At-least-once로 전달된 원시 사용량을 잃지 않고 저장하며, 회사–VM 점유 이력과 결합된 귀속 조회 모델을 통해 테넌트 격리된 비용 조회와 월간 재계산을 안전하게 지원한다.

실행 가능한 정의는 [`database/clickhouse/schema.sql`](../database/clickhouse/schema.sql)에 두되, 이번 저장 단위 변경은 아직 반영하지 않았다. 기준 버전은 ClickHouse `26.3 LTS`다.

## 2. 선택

| 대상 | 선택 | 근거 |
|---|---|---|
| 원시 사용량 원장 | 이벤트당 1행의 `MergeTree` 전달 사본 (테넌트 비인지) | 사용량 3개를 배열로 유지해 수신·식별·재전달 단위를 일치시킨다. 회사 식별자는 넣지 않는다. |
| 원시 원장 파티션 | 사용 시작 UTC 월 (`toYYYYMM(charge_period_start)`) | 월간 수명주기·재계산 단위와 일치하며 파티션 수가 제한된다. |
| 원시 원장 정렬 | 출처(`event_source`) → 사용 시각(`charge_period_start`) → 이벤트 ID(`event_id`) | VM 출처·기간 필터와 이벤트 중복 판별을 지원한다. 효과는 실행 계획과 부하로 검증한다. |
| 논리 사용량 읽기 | 내부 전용 일반 `VIEW` | 이벤트 중복 제거 후 필요 시 서비스별로 펼친다. 결과 사본·갱신 작업은 두지 않는다. |
| 귀속 조회 모델 | 테넌트 격리 조회 모델 (Row Policy 적용) | 점유 이력으로 회사를 확정한 조회 모델이다. BFF는 이 모델만 읽으며 테넌트별 DB 신원과 Row Policy로 자기 회사 행만 허용한다. (물리 형태는 3단계에서 확정) |
| 가격 사본 | `ReplacingMergeTree(sync_version)` | PostgreSQL 가격의 수정 사본을 버전으로 교체하며 작은 테이블만 `FINAL`로 읽는다. |
| 선집계 | 사용하지 않음 | 먼저 요청 시 집계 성능을 측정하고 한계에 도달할 때만 추가한다. |

`ReplacingMergeTree`의 중복 제거는 백그라운드 merge 시점에 의존하므로 원시 사용량 정확성의 근거로 삼지 않는다. 공식 문서도 merge만으로 중복 부재를 보장하지 않는다고 명시한다: [ReplacingMergeTree](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/replacingmergetree).

## 3. 원시 사용량 원장

목표 `usage_record_delivery` 한 행은 Kafka에서 전달된 이벤트 하나다. 내부의 Compute·Storage·Network 측정값 3개를 배열로 보존한다. 배열의 구체 자료형과 열 매핑은 학습·승인 후 구현한다.

- 재전송이 없다면 월 8.6억 이벤트는 원장 8.6억 행이다. 읽을 때 모두 펼치면 약 25.8억 논리 사용량 항목이 된다. 재전달 사본은 원장 행 수를 늘린다.
- 이벤트 중복 제거 키: `event_source + event_id`
- 물리 전달 식별자: `kafka_topic + kafka_partition + kafka_offset` (재처리 시 같은 전달도 여러 행으로 저장될 수 있음)
- 펼친 뒤의 논리 사용량 키: `event_source + event_id + meter`
- Kafka 파티션 key는 `event_source`다. 이벤트 식별자 `event_source + event_id`와 구분한다.
- 동일 이벤트 키의 내용은 발생기가 유지한다. 기존 `payload_hash` 열의 전환 여부는 구현 시 다루며 별도 충돌 검사는 현재 수집 범위에서 제외한다.
- 원시 원장에는 `billing_account_id`를 저장하지 않으며, BFF 계정의 접근을 원천 차단한다.
- 일반 뷰에서 이벤트 키별 전달 사본 하나를 선택해 내용 전체를 함께 읽는다. 기존 전달 위치 기준 선택은 유지하되 SQL은 이벤트 단위로 전환한다. 적재 전 제거하거나 원시 행을 삭제하는 방식은 아니다.
- 소비 완료는 적재 묶음의 디스크 동기화 이후다. 실제 설정·실패 동작은 [저장소 계약](storage-access-contract.md#3-이벤트-적재)에 따라 검증하며 현재 SQL에 적용 완료된 것은 아니다.

### 중복 제거용 일반 뷰

이벤트 단위 원장 → 일반 뷰로 `source + id`별 이벤트 하나 선택 → 필요한 서비스별 사용량 전개·회사 귀속 → 비용 계산 순서다. 중복 제거 때 측정값 3개를 함께 보존하며, 단위가 다른 수량을 그대로 합산하지 않는다.

- 귀속 처리는 공통 뷰를 사용하고 중복 제거 SQL을 개별 경로에 복제하지 않는다. BFF는 이 뷰도 직접 읽지 못하며 귀속 완료 모델만 읽는다.
- 일반 뷰는 SQL만 저장하므로 결과 사본의 동기화·재생성 부담이 없다. 대신 읽을 때마다 중복 제거 비용을 부담한다. [ClickHouse 일반 뷰](https://clickhouse.com/docs/reference/statements/create/view#normal-view)
- 이는 규칙 공유를 위한 기준선이지 성능 보장이 아니다. 중복 제거·배열 전개 비용도 측정하며 목표 미달 시 원인을 확인한 뒤 최적화한다.
- Kafka 적재용 Materialized View의 연결 역할은 별개다. 수집 시 3행으로 펼치지 않는다는 결정이지, 적재용 MV를 일반 뷰로 대체하는 결정은 아니다.

### 저장 단위의 선택과 트레이드오프

| 선택지 | 이점 | 부담 |
|---|---|---|
| A. 이벤트 단위 저장 — 선택 | 수신·식별·재전달과 저장 단위가 같고 이벤트 전체를 한 번 선택한다. | 서비스별 처리 시 배열 전개가 필요하다. |
| B. 서비스별 행 저장 | 서비스별 필터·조인·집계 SQL이 단순하다. | 적재 시 전개하며 중복 제거도 서비스별 행 단위로 다룬다. |

서비스별 조회는 필요하지만 원시 원장을 즉시 펼쳐 저장할 의무는 없다. BFF는 귀속 완료 모델만 읽는다. A로 시작해 성능을 측정하고, 병목이 확인되면 관련 엔진 동작을 학습하며 개선한다. 행 수만으로 저장량·성능 개선을 단정하지 않는다.

## 4. 가격 사본

`price_rate_snapshot`은 PostgreSQL `price_rate`의 재생성 가능한 사본이다.

- `sync_version`이 큰 사본이 최신이다.
- SKU의 서비스·meter·unit도 함께 복사해 사용량 계약과 조인한다.
- 조회와 배치는 작은 가격 테이블에만 `FINAL`을 사용한다.
- 사용 구간을 완전히 포함하는 가격이 정확히 하나여야 한다.
- 가격 변경 시각을 걸치는 60초 사용 구간의 정책은 미결이다. 임의로 분할하거나 한 가격을 선택하지 않는다.
- 가격이 없거나 겹치면 0원으로 처리하지 않고 조회·배치를 실패시킨다.
- 가격 동기화와 배치 확정은 PostgreSQL 가격 버전을 기준으로 검증한다.

## 5. 조회 영향 및 테넌트 격리

| 조회 | 물리 구조의 지원 |
|---|---|
| 원시 원장 적재·귀속 | `event_source` 및 시간 정렬로 점유 이력 매핑과 중복 제거 지원 |
| 월 누적·기간 비용 | 회사·기간 범위를 줄이는 물리 구조가 필요하며 정렬 키는 미정 |
| 서비스 구성·추이 | 회사 범위 내 서비스·시간 그룹화를 지원해야 함 |
| 리소스 Top N·상세 | 회사 범위 내 리소스 필터·그룹화를 지원해야 함 |
| 원본 커서 | `charge_period_end, event_source, event_id, meter` 안정 정렬 |
| 월간 재계산 | 해당 월 파티션과 점유 이력 결합 스캔 |

- ClickHouse의 `ORDER BY`는 디스크 정렬과 sparse index를 결정한다.
- BFF는 테넌트별 DB 신원으로 ClickHouse에 연결하며, Row Policy가 귀속 모델에서 타 테넌트 행을 차단한다.
- 테넌트별 파티션이나 테넌트별 물리 테이블 분할은 하지 않고 단일 공유 테이블/뷰 구조를 유지한다.

## 6. 검증 기준

- 같은 이벤트를 반복 적재해도 중복 제거 후 사용량과 비용이 변하지 않아야 한다.
- 순서를 바꿔 적재해도 사용 시각 기준 결과가 같아야 한다.
- 점유 이력 구간(`[validFrom, validTo)`)과 결합해 정확한 회사로 귀속되어야 한다.
- BFF 계정으로 원시 원장(`usage_record_delivery`) 또는 중복 제거용 일반 뷰에 접근 시 권한 거부(Permission Denied)되어야 한다.
- 테넌트별 DB 신원으로 조회 시 다른 회사의 데이터가 일절 노출되지 않아야 한다.
- 가격 사본의 이전 버전이 남아 있어도 최신 버전 하나만 선택돼야 한다.
- 31일 조회와 월간 배치가 함께 실행될 때 목표 응답시간과 자원 한도를 부하 테스트로 검증한다.
