# Implementation Roadmap

## 1. 원칙

- 문서 영역을 한 번에 모두 구현하지 않고, 실행 가능한 수직 기능을 차례로 완성한다.
- 각 구현 전에 설계 패턴·프레임워크 동작·Java·CS 원리를 학습한다.
- 사용자가 핵심 질문을 정확히 설명하고 승인한 뒤에만 구현한다.
- 구현 후 작은 정확성 테스트를 통과하고 작업 단위로 커밋·푸시한다.
- 선집계·Redis·추가 서비스는 측정 결과가 요구할 때만 도입한다.

| 단계 | 상태 | 결과물 | 완료 기준 |
|---|---|---|---|
| 0. 설계 기반 | 완료 | 요구사항·계약·ADR·물리 모델 | DB 스키마와 대표 쿼리 실행 통과 |

## 3. 학습 승인 게이트

각 구현 단위는 다음 순서를 지킨다.

```text
요구사항 확인
→ 동작 원리와 관련 CS 학습
→ 선택지·트레이드오프 설명
→ 실패 사례와 테스트 기준 확인
→ 사용자가 자신의 말로 설명
→ 오해가 없을 때 사용자 승인
→ 구현·테스트·커밋·푸시
```

이해 확인은 용어 암기가 아니라 다음 네 가지를 설명할 수 있는지 본다.

1. 왜 이 기능이 필요한가
2. 내부에서 어떤 순서로 동작하는가
3. 어떤 실패가 가능하고 어떻게 막는가
4. 다른 선택지 대신 이 방식을 택한 이유는 무엇인가

답변에 기능을 바꿀 정도의 오해가 있으면 구현하지 않고 해당 부분만 다시 학습한다.

## 4. 구현 단위

```text
usage-event-api       : 인증·검증 후 Kafka 기록
usage-ledger-writer   : Kafka 소비 후 ClickHouse 원장 적재
settlement-batch      : 월간 검증·재시도·확정
billing-bff           : 세션·RBAC·비용·정산 API
billing-web           : 대시보드
usage-generator       : 정상·중복·지연·부하 이벤트 발생
```

공통 코드는 이벤트 계약과 계산 값 타입처럼 실제 공유가 필요한 범위로 제한한다.

## 5. 다음 작업

단계 3을 다음 학습·구현 단위로 나눈다.

1. Spring Session JDBC와 세션 쿠키·CSRF
2. 로그인·로그아웃과 세션 고정 공격 방어
3. 요청별 소속·역할 복원과 Spring Security
4. PostgreSQL 트랜잭션 컨텍스트와 RLS
5. Viewer·Admin Method Security와 감사·세션 폐기

현재는 1번의 학습을 시작하기 전이며, 사용자 승인 전에는 관련 구현을 진행하지 않는다.
