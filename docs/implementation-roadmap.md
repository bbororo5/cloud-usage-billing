# Implementation Roadmap

## 1. 목표와 진행 원칙

Java 21 기반 사용량 과금 포트폴리오다. 도메인 확장보다 데이터 파이프라인·DBMS·배치·보안·측정 역량을 보여준다.

각 구현 단계는 **설명 → 사용자 이해 확인 → 구현 승인 → 작은 구현·검증 → 커밋** 순서로 진행한다. 문서 승인은 구현 전체의 승인이 아니다.

성능 개선은 **측정 → 병목과 관련 엔진 동작 학습 → 한 가지 변경 → 같은 조건으로 재검증** 순서로 진행한다. 정확한 기준 구현부터 만들고 데이터를 단계적으로 늘려 관찰하며, 마지막 단계까지 측정을 미루지 않는다. 관찰 근거와 개선 전후 수치를 포트폴리오에 남긴다. 성능을 위해 중복 과금 방어·내구성·테넌트 격리를 완화하지 않는다.

## 2. 현재 위치

목표 구조는 **VM 발생기 → Kafka → ClickHouse 직접 소비**다. 웹·BFF·월간 배치와 PostgreSQL을 함께 둔다. 접수 API와 독립 원장 적재기는 목표에서 제외한다. [C2](diagrams/c2-containers.svg)는 이 목표를 표시하며 구현 완료도가 아니다.

사용량 공유 토픽 하나를 유지한다. 운영자 관리 발생기의 출처·측정값을 신뢰하며 ClickHouse 수집은 저장·중복 반영 방어에 집중한다. 별도 내용 검증·자동 격리는 제외한다. 향후 입력 격리 요구가 강화되거나 직접 소비의 복구 요구를 충족하기 어려우면 중간 처리 서버를 재검토한다. 점유 제어는 별도 토픽이다. (ADR-010 보완 승인)

| 구분 | 현재 상태 |
|---|---|
| 설계 기반 | 요구사항·품질·논리 경계·주요 ADR 수립. 아래 미결 항목은 남음 |
| 실행 기반 | Java·로컬 저장소·모듈 기반 구현 |
| 수집 | 이전 API·적재기·서비스별 행 원장의 구현 이력이 있음. 직접 소비·이벤트 단위 원장 전환은 미구현 |
| 점유·귀속 | 생명주기·캐시 일관성·오류 차단 원칙 승인. 상태·물리 구조·실행 배치 미구현 |
| 사용자 조회·보안 | API·세션·RLS·Row Policy 계약 수립. 귀속 모델에 연결한 전체 검증 전 |
| 월간 배치·웹·성능 | 후속 구현 단계 |

기존 API·발생기 인증·usage-ledger-writer 코드와 deprecated OpenAPI는 전환 전 기반이다. 과거 검증을 새 경로의 성공 증거로 사용하지 않는다. 60초 측정·독점 확보 과금 등 후속 규칙도 코드 반영 여부를 확인해야 한다.

## 3. 남은 순서

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 2. 수집 전환 | 직접 producer와 ClickHouse 내장 소비 검증, 이전 경로 정리 | 발생기 계약 준수, 브로커 접근 통제, 재시작·중복·적재 내구성·offset 복구 검증 |
| 3. 점유·귀속 | 제어 상태·이력·캐시·귀속 모델과 오류 복구 | 과거 회사 귀속, 변경 중 공개 차단, 재처리 후 동일 결과 |
| 4. 비용·보안 API | 요청 시 집계, 세션·현재 역할·저장소 격리 | 기간/서비스/자원 조회와 교차 테넌트 공격 테스트 통과 |
| 5. 월간 정산 | 회사·월 작업, 재계산·검증·원자적 확정 | 실패 재시도, 차이 0원, 부분 확정 없음 |
| 6. 웹 대시보드 | 예상·확정 비용과 권한 화면 | API 계약에 맞는 사용자 흐름 |
| 7. 성능·포트폴리오 | 동시 조회·배치·장애 실험, 병목 개선 | 재현 가능한 수치와 개선 전후 근거 |

수집의 발행·신뢰, 검증 범위, 저장 완료, 중단·복구 정책을 확정했다. 디스크 동기화 후 offset을 진행하고, 재시작은 같은 그룹의 확정 위치를 따른다. 지속 실패는 알리되 폐기·건너뛰지 않는다. 발생기 재시작 복구·브로커 인증·동기화·재시도·알림·보관의 구체 구성은 남아 있다. 구현은 학습·승인 후 진행한다.

2026-09-16 **A. 이벤트 단위 저장**을 승인했다. 원장은 이벤트당 1행에 측정값 배열을 보존한다. 내부 일반 뷰에서 `source + id`별 이벤트 전체를 하나 선택하고 필요할 때 서비스별로 펼친다. BFF는 귀속 완료 모델만 읽는다. 원장 전환·뷰 SQL·권한·성능은 미구현·미검증이다.

현재는 ClickHouse 기초 학습 중이며 SQL 예제는 설명만 했고 실행하지 않았다. 다음은 이벤트 단위 저장·중복 제거를 작은 예제로 확인한 뒤 Kafka 적재 연결과 실패 지점을 구체화한다. 기존 3행 전개를 수집 필수 단계로 다시 전제하지 않는다.

## 4. 미결 사항

| 판단 | 필요한 이유 |
|---|---|
| 60초 사용 구간의 조회·월·가격 경계 처리 | 이벤트는 점유 시작 기준, API는 UTC 분 경계·월간 정산은 UTC 월이다. 완전 포함 조건만 쓰면 걸친 구간이 누락될 수 있다. 분할·귀속 정책은 아직 선택하지 않았다. |
| 직접 소비의 저장·멱등성·복구 | 이벤트 단위 저장·일반 뷰 중복 제거와 복구 정책은 승인했다. 배열 자료형·열 매핑, 적재 연결·뷰 SQL·권한, 재시도·알림·보관 수치와 실제 장애·성능 검증은 남아 있다. |
| 점유 제어·귀속·캐시의 최소 실행/저장 구조 | 원장·캐시 변경 중 공개 보류, 재시작, 버전 비교, 종료 사실의 Kafka 기록 전 장애를 방어해야 한다. |
| 귀속 모델과 이력 정정 | 원시 데이터는 BFF에 노출하지 않는다. 재귀속 시 이중 공개를 막는 물리 모델이 필요하다. |
| 회사 불명 귀속 오류의 정산 차단 범위 | 해결 전 확정 금지는 유지하되 어느 회사·월 작업을 막을지 정해야 한다. |
| 지연 목표의 측정 구간 | 품질 시나리오의 정상 반영 10초·1분과 부하 중 허용 5분을 각각 어느 구간에서 측정할지 명시해야 한다. 수치는 임의로 완화하지 않는다. |

인증은 현재 서버 세션이다. JWT·캐시 제품·선집계·추가 실행 단위는 새 승인 없이 도입하지 않는다.

## 6. 새 세션 인계 프롬프트

> 이 저장소의 AGENTS.md와 docs/implementation-roadmap.md를 먼저 읽고 관련 계약·ADR만 추가 확인해줘. 목표는 발생기 → 공유 Kafka 토픽 → ClickHouse 직접 소비야. 신뢰 입력, 디스크 동기화 후 offset 진행, 확정 위치 복구·폐기 금지는 승인됐어. 원장은 A안인 이벤트당 1행·측정값 배열 보존으로 바꿨어. 일반 뷰에서 source + id별 이벤트 전체를 선택한 뒤 필요할 때 서비스별로 펼쳐. BFF는 귀속 완료 모델만 읽어. 기존 API·적재기·서비스별 행 SQL은 전환 전 코드야. 나는 일반 SQL은 익숙하지만 ClickHouse는 처음이고, 지금까지 예제는 설명만 했어. 다음은 이벤트 단위 저장·중복 제거를 작은 예제로 확인한 뒤 Kafka 연결·실패 지점을 구체화해. 성능은 먼저 측정하고 병목과 관련 엔진 동작을 함께 학습하며 개선해. 구현 전에 내 이해와 승인을 확인하고, 작은 단위로 검증·커밋 후 푸시해.
