# Implementation Roadmap

## 1. 목표와 진행 원칙

Java 21 기반 사용량 과금 포트폴리오다. 도메인 확장보다 데이터 파이프라인·DBMS·배치·보안·측정 역량을 보여준다.

진행 순서는 **HLD·계약 가드레일 → 흐름별 내부·연결 LLD와 테스트 설계 → 사용자 이해 확인·승인 → TDD 구현·통합 검증 → 커밋**이다. 입력·상태·장애 시점을 분해하고, 중요한 오류를 검출할 수 있는 저비용 오라클을 선택한다. 실패 확인 → 최소 구현 → 리팩터링·회귀 검증을 반복한다. 문서 승인은 구현 전체의 승인이 아니며, 테스트 기반 작성과 제품 기능 구현을 구분한다.

성능 개선은 **측정 → 병목과 관련 엔진 동작 학습 → 한 가지 변경 → 같은 조건으로 재검증** 순서로 진행한다. 정확한 기준 구현부터 만들고 데이터를 단계적으로 늘려 관찰하며, 마지막 단계까지 측정을 미루지 않는다. 관찰 근거와 개선 전후 수치를 포트폴리오에 남긴다. 성능을 위해 중복 과금 방어·내구성·테넌트 격리를 완화하지 않는다.

## 2. 현재 위치

목표 구조는 **VM 발생기 → Kafka → ClickHouse 직접 소비**다. 웹·BFF·월간 배치와 PostgreSQL을 함께 둔다. 접수 API와 독립 원장 적재기는 목표에서 제외한다. [C2](diagrams/c2-containers.svg)는 이 목표를 표시하며 구현 완료도가 아니다.

사용량 공유 토픽 하나를 유지한다. 운영자 관리 발생기의 출처·측정값을 신뢰하며 ClickHouse 수집은 저장·중복 반영 방어에 집중한다. 별도 내용 검증·자동 격리는 제외한다. 향후 입력 격리 요구가 강화되거나 직접 소비의 복구 요구를 충족하기 어려우면 중간 처리 서버를 재검토한다. 점유 제어는 별도 토픽이다. (ADR-010 보완 승인)

| 구분 | 현재 상태 |
|---|---|
| 설계 기반 | 요구사항·품질·논리 경계·주요 ADR 수립. 아래 미결 항목은 남음 |
| HLD 가드레일 | 이벤트·API 계약 110건, PostgreSQL 접근 112건, 모듈 경계 검증 13건과 실제 의존 검사 통과·CI 연결. 실제 응답·ClickHouse 격리는 후속 LLD에 맞춰 추가 |
| 실행 기반 | Java·로컬 저장소·모듈 기반 구현 |
| 수집 | 직접 발행·Kafka 내장 소비·이벤트 1행 원장·중복 제거 뷰 구현. 로컬 통합·실패 복구·접근 거부 검사 통과. 전원 장애·대규모 성능은 미검증 |
| 점유·귀속 | 생명주기·캐시 일관성·오류 차단 원칙 승인. 상태·물리 구조·실행 배치 미구현 |
| 사용자 조회·보안 | API·세션·RLS·Row Policy 계약 수립. 귀속 모델에 연결한 전체 검증 전 |
| 월간 배치·웹·성능 | 후속 구현 단계 |

이전 API·적재기·파서는 `legacy/`로 이동하고 빌드에서 제외했다. 발생기는 완료된 점유 구간의 60초 이벤트를 생성·재생하는 운영자 시뮬레이터다. 실제 VM 측정과 점유 제어는 구현하지 않았다. 이번 수집 위임을 후속 기능 구현 승인으로 확대하지 않는다.

## 3. 남은 순서

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 2. 수집 검증 보완 | 기준 구현·로컬 복구 검증 완료. 전원 장애·성능·운영 배포 검증 별도 | 미검증 범위를 근거 없이 완료 처리하지 않음 |
| 3. 점유·귀속 | 제어 상태·이력·캐시·귀속 모델과 오류 복구 | 과거 회사 귀속, 변경 중 공개 차단, 재처리 후 동일 결과 |
| 4. 비용·보안 API | 요청 시 집계, 세션·현재 역할·저장소 격리 | 기간/서비스/자원 조회와 교차 테넌트 공격 테스트 통과 |
| 5. 월간 정산 | 회사·월 작업, 재계산·검증·원자적 확정 | 실패 재시도, 차이 0원, 부분 확정 없음 |
| 6. 웹 대시보드 | 예상·확정 비용과 권한 화면 | API 계약에 맞는 사용자 흐름 |
| 7. 성능·포트폴리오 | 동시 조회·배치·장애 실험, 병목 개선 | 재현 가능한 수치와 개선 전후 근거 |

현재는 **수집 기준 구현과 로컬 통합 검증을 마친 상태**다. [수집 구현·검증](ingestion-implementation.md)에 실행법·설정·증거·한계를 정리했다. 발생기 재실행, Kafka 재전달, ClickHouse 저장 실패·강제 종료·복구와 BFF 원본 접근 거부를 검사했다. 전원 장애·fsync 호출 실패·디스크 영구 손실·보관 만료·대용량은 별도 검증이다. 경고는 콘솔/종료 코드이며 외부 알림 연동은 아직 없다.

다음 기능 단계는 **점유 이력을 통한 회사 귀속**이다. 원장·중복 제거·ACK 책임을 다시 설계하지 않는다. 점유 제어·캐시·귀속 모델은 사용자 학습·승인 후 구현한다. 기존 PostgreSQL 권한 수정과 이전 ClickHouse 데이터의 개발 볼륨 마이그레이션은 수행하지 않았다.

## 4. 미결 사항

| 판단 | 필요한 이유 |
|---|---|
| 60초 사용 구간의 조회·월·가격 경계 처리 | 이벤트는 점유 시작 기준, API는 UTC 분 경계·월간 정산은 UTC 월이다. 완전 포함 조건만 쓰면 걸친 구간이 누락될 수 있다. 분할·귀속 정책은 아직 선택하지 않았다. |
| 수집의 운영 검증 | 구현·로컬 장애 검증과 전원 장애·디스크 영구 손실·장기 보관·대규모 성능 검증을 구분한다. 운영 TLS·비밀 관리·외부 알림도 후속 작업이다. |
| 점유 제어·귀속·캐시의 최소 실행/저장 구조 | 원장·캐시 변경 중 공개 보류, 재시작, 버전 비교, 종료 사실의 Kafka 기록 전 장애를 방어해야 한다. |
| 귀속 모델과 이력 정정 | 원시 데이터는 BFF에 노출하지 않는다. 재귀속 시 이중 공개를 막는 물리 모델이 필요하다. |
| 회사 불명 귀속 오류의 정산 차단 범위 | 해결 전 확정 금지는 유지하되 어느 회사·월 작업을 막을지 정해야 한다. |
| 지연 목표의 측정 구간 | 품질 시나리오의 정상 반영 10초·1분과 부하 중 허용 5분을 각각 어느 구간에서 측정할지 명시해야 한다. 수치는 임의로 완화하지 않는다. |

인증은 현재 서버 세션이다. JWT·캐시 제품·선집계·추가 실행 단위는 새 승인 없이 도입하지 않는다.
