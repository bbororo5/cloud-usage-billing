# Implementation Roadmap

## 1. 목표와 진행 원칙

Java 21 기반 사용량 과금 포트폴리오다. 도메인 확장보다 데이터 파이프라인·DBMS·배치·보안·측정 역량을 보여준다.

전체 작업은 **시스템 → C2 컨테이너 → 책임 → 검증 가능한 작업**으로 분해한다. 분해 후 기존 구현·테스트와 대조해 상태를 표시하고, 의존 관계에서 실행 순서를 정한다. 도메인 책임과 컨테이너는 일대일이 아니며, 기능 하나의 완료를 컨테이너 전체의 완료로 표시하지 않는다.

진행 순서는 **HLD·계약 가드레일 → 관련 컨테이너의 내부·연결 LLD와 테스트 설계 → 사용자 이해 확인·승인 → TDD 구현·통합 검증 → 커밋**이다. 입력·상태·장애 시점을 분해하고, 중요한 오류를 검출할 수 있는 저비용 오라클을 선택한다. 실패 확인 → 최소 구현 → 리팩터링·회귀 검증을 반복한다. 문서 승인은 구현 전체의 승인이 아니며, 테스트 기반 작성과 제품 기능 구현을 구분한다.

성능 개선은 **측정 → 병목과 관련 엔진 동작 학습 → 한 가지 변경 → 같은 조건으로 재검증** 순서로 진행한다. 정확한 기준 구현부터 만들고 데이터를 단계적으로 늘려 관찰하며, 마지막 단계까지 측정을 미루지 않는다. 관찰 근거와 개선 전후 수치를 포트폴리오에 남긴다. 성능을 위해 중복 과금 방어·내구성·테넌트 격리를 완화하지 않는다.

## 2. 작업 분해 초안

목표 구조는 **VM 발생기 → Kafka → ClickHouse 직접 소비**다. 웹·BFF·월간 배치와 PostgreSQL을 함께 둔다. 접수 API와 독립 원장 적재기는 목표에서 제외한다. [C2](diagrams/c2-containers.svg)는 이 목표를 표시하며 구현 완료도가 아니다.

사용량 공유 토픽 하나를 유지한다. 운영자 관리 발생기의 출처·측정값을 신뢰하며 ClickHouse 수집은 저장·중복 반영 방어에 집중한다. 별도 내용 검증·자동 격리는 제외한다. 향후 입력 격리 요구가 강화되거나 직접 소비의 복구 요구를 충족하기 어려우면 중간 처리 서버를 재검토한다. 외부가 확정한 점유 시작·종료 사실은 별도 토픽이다. (ADR-009·010 경계 보완)

VM 할당·전원 감지·활성화·요청 만료·재할당 승인은 외부 인프라 책임이다. 내부는 점유 사실을 이력에 반영하고 사용량을 회사에 연결한다. 캐시 지연으로 VM 동작을 막지 않으며 미확인 귀속 결과의 공개를 보류한다.

각 말단 항목은 **작업 → 검증할 결과**다. 완료·미완료 목록이 아니라 전체 범위이며, 이미 구현한 작업도 포함한다. 번호는 실행 순서가 아니다. 클래스·패키지·새 컨테이너는 여기서 결정하지 않는다. 각 항목의 설계·구현·검증 근거는 같은 순서의 [작업별 상태표](implementation-status.md)에 둔다.

### 2.1 VM 발생기 — 외부 시스템

- **사용량 생성**
  - 점유 구간을 60초 이벤트로 변환 → 회사 정보 없이 세 측정값을 담고 잔여 구간·유휴 구간은 발행하지 않는다.
- **전송 책임**
  - Kafka 발행과 ACK 처리 → ACK를 받은 이벤트만 전송 성공으로 판정한다.
  - 실패·응답 유실 후 재전송 → 동일 논리 이벤트의 식별자와 내용이 유지된다.

실제 VM 측정·제어는 제외한다. 점유 경계 신호는 외부 인프라가 제공하며 발생기에 회사 판단을 넣지 않는다. 내부의 점유 사실 수신·이력 반영은 2.8에서 다룬다.

### 2.2 Kafka

- **내구 기록**
  - 사용량 토픽·복제·ACK 조건 설정 → 브로커 장애와 ISR 부족 시 계약대로 성공하거나 거부한다.
  - 발행·소비 권한 제한 → 잘못된 자격증명과 허용하지 않은 토픽 접근을 거부한다.
- **재처리 기반**
  - 보관·소비 위치 정책 적용 → 보관 범위 안에서 재개하고, 위치 누락·범위 이탈을 조용히 건너뛰지 않는다.
  - 점유 사실 토픽 구성 → 사용량과 분리하고 같은 VM의 시작·종료 사실을 같은 파티션으로 전달한다. 두 토픽 간 순서를 보장하지는 않는다.

### 2.3 ClickHouse

- **원시 이벤트 보존**
  - 이벤트 단위 적재와 commit 연결 → 저장 실패 시 소비 위치를 확정하지 않고 복구 후 재적재한다.
  - 일반 뷰에서 중복 제거 → 재전달 횟수와 무관하게 논리 이벤트와 세 측정값을 한 번 반영한다.
- **귀속 데이터 제공**
  - 귀속 결과 저장·정정 모델 정의 → 공개 가능한 귀속 결과만 조회되고 재귀속 시 양 회사에 동시에 노출되지 않는다.
  - 테넌트별 신원·Row Policy 적용 → 다른 회사 데이터와 원시 원장에 대한 BFF 접근을 거부한다.
- **조회 계산**
  - 가격 사본 적재·버전 확인 → 재동기화해도 중복 계산하지 않고 누락·불일치를 검출한다.
  - 기간·서비스·자원별 집계 SQL 작성 → 승인된 시간 경계·가격·정밀도 규칙과 기준 계산 결과가 일치한다.
  - 귀속 완료 사용량 상세 조회 → 고정된 조회 기준과 정렬 키로 커서 페이지를 이어간다.

귀속 회사의 판단·공개 승인 주체는 2.8에서 정한다. 가격 사본 동기화 실행 주체도 그곳에서 배정한다.

### 2.4 PostgreSQL

- **운영 원장 보존**
  - 사용자·회사 소속·역할 제약 적용 → 잘못된 소속 관계와 마지막 Admin 제거를 차단한다.
  - 점유 이력·버전 제약 적용 → 중복 점유를 막고 종료 후에도 과거 관계를 보존한다.
  - 가격 원본·export 제공 → 유효 기간별 가격과 동기화 버전을 식별할 수 있다.
  - 정산 실행·확정 결과 보존 → 회사·월 중복 확정과 완료 결과 덮어쓰기를 차단한다.
- **저장소 접근·변경 통제**
  - 앱별 권한·RLS 적용 → 회사 범위 누락·다른 회사 접근·과도한 쓰기를 거부한다.
  - 스키마·권한 마이그레이션 검증 → 신규 설치와 기존 데이터 보존을 각각 확인한다.

DB 제약은 처리 주체가 아니다. 점유 사실 반영은 2.8, 정산 실행은 2.6이 담당한다.

### 2.5 BFF · 인증/인가

- **인증·권한 확인**
  - 로그인·로그아웃·본인 정보 연결 → 유효 세션만 인정하고 상태 변경 요청의 CSRF를 검사한다.
  - 현재 소속·역할을 조회 범위에 연결 → 클라이언트의 회사 지정 없이 두 DB에 일관된 범위를 적용한다.
  - 구성원 역할 관리 → Admin만 자기 회사 역할을 변경하고 변경·거부를 기록한다.
- **조회 API 제공**
  - 비용·정산·사용량 API 연결 → 계약의 필터·그룹·정렬·한도와 커서 변조 검사를 적용한다.
  - 응답·오류 조합 → 기준 시각을 제공하고 계산 불가를 0원으로 숨기거나 내부 정보를 노출하지 않는다.

### 2.6 월간 정산 배치

- **실행 관리**
  - 회사·월 작업 시작·재시도 → 같은 작업의 동시 실행을 막고 실패를 새 실행 이력으로 재처리한다.
  - 정산 준비 확인 → 적체·적재 지연·미해결 귀속 오류가 남으면 관련 확정을 보류한다.
- **검증·확정**
  - 원본 기반 재계산 요청·비교 → 조회와 같은 계산 규칙으로 가격 일치·데이터 이상·금액 차이를 검증한다.
  - 검증 결과와 금액을 원자적으로 확정 → 중간 실패 시 부분 결과를 공개하지 않고 기존 확정을 유지한다.

### 2.7 웹 대시보드

- **비용 탐색**
  - 예상 비용·기간 필터·사용량 상세 연결 → 요청 조건과 표시 결과·기준 시각이 일치한다.
  - 월간 확정 결과 표시 → 예상액·확정액·미확정 상태를 구분한다.
- **접근 상태 표현**
  - 로그인·역할별 화면 연결 → 세션 만료·접근 거부·조회 실패를 표시하고 Admin에게만 관리 화면을 제공한다.
  - 구성원 역할 변경 화면 연결 → 서버의 변경 결과·거부 사유에 맞게 화면 상태를 갱신한다.

화면 숨김은 권한 방어가 아니다. 실제 허용 여부는 BFF와 저장소가 검사한다.

### 2.8 실행 위치 미정인 책임 — 컨테이너가 아님

- **점유 이력**
  - 외부 점유 사실 수신 계약 → 사건·점유 대상·실제 시각·회사 관계를 식별하고 지연 사실을 요청 TTL로 폐기하지 않는다.
  - 시작·종료 이력 반영 → 겹치는 이력을 정상으로 수용하지 않고, 실제 종료 시각을 보존하며 이전 점유 종료로 새 이력을 닫지 않는다.
- **이력·캐시 일관성**
  - 제어 사건의 멱등 반영·버전 비교 → 중복·역순 처리로 과거 상태가 최신 이력을 덮어쓰지 않는다.
  - 변경 중 공개 보류·재시작 복구 → 필요한 사실의 원장·캐시 반영이 확인되기 전 영향 구간을 공개하지 않는다. 외부 재할당은 막지 않는다.
- **사용량 귀속**
  - 사용 구간을 점유 이력과 연결 → 지연 도착도 당시 회사에 귀속하고 캐시 누락 시 원장을 확인한다.
  - 미귀속·중복 점유 처리 → 원본·오류를 보존하고 알림·공개 차단·정산 차단 후 수정 이력으로 재처리한다.
  - 확정된 월의 지연 이벤트 처리 → 원본을 보존·격리하고 확정 금액을 변경하지 않는다.
- **가격 동기화 실행**
  - PostgreSQL export → ClickHouse 사본 반영·검증 → 계산에 필요한 가격 버전이 준비되기 전 서비스를 계산 가능 상태로 공개하지 않는다.

점유 이력(캐시 포함)·사용량 귀속을 모듈 후보로 둔다. [불변식과 변경 권한](logical-data-model.md#불변식에서-도출한-모듈-후보)을 바탕으로 연결 계약을 정한 뒤 실행 위치를 배정한다. 가격 동기화의 실행 위치도 별도 확인한다. 이 분류는 새 서비스를 뜻하지 않는다.

## 3. 현재 위치와 후속 정리

**공통 기반:** 요구사항·품질·논리 경계·주요 ADR과 Java 실행 기반을 마련했다. 이벤트·API 계약 110건, PostgreSQL 접근 112건, 모듈 경계 13건과 실제 의존 검사가 통과했고 CI에 연결했다. 계약 검사는 실제 API 응답이나 전체 테넌트 격리 검증의 완료를 뜻하지 않는다.

이전 API·적재기·파서는 `legacy/`로 이동하고 빌드에서 제외했다. 발생기는 완료된 점유 구간의 60초 이벤트를 생성·재생하는 운영자 시뮬레이터다. 실제 VM 측정·제어는 외부 범위이며, 점유 사실 입력·내부 이력 반영은 미구현이다. 이번 수집 위임을 후속 기능 구현 승인으로 확대하지 않는다.

현재는 **수집 기준 구현과 로컬 통합 검증을 마친 상태**다. [수집 구현·검증](ingestion-implementation.md)에 실행법·설정·증거·한계를 정리했다. 발생기 재실행, Kafka 재전달, ClickHouse 저장 실패·강제 종료·복구와 BFF 원본 접근 거부를 검사했다. 전원 장애·fsync 호출 실패·디스크 영구 손실·보관 만료·대용량은 별도 검증이다. 경고는 콘솔/종료 코드이며 외부 알림 연동은 아직 없다.

분해한 각 작업의 설계·구현·검증 근거를 [상태표](implementation-status.md)에 연결했다. **PostgreSQL 점유 이력 테이블은 미구현이며, BFF·배치는 실행 뼈대만 있다.** DB 제약과 계약 테스트 통과를 업무 기능의 완료로 보지 않는다.

다음은 **점유 이력·사용량 귀속 사이의 공개 안전성 계약을 정하는 것**이다. 특히 점유 사실보다 사용량이 먼저 도착한 경우를 다룬다. 불변식 → 모듈 책임·연결 계약 → 실행 위치·데이터 모델·선후관계 순으로 진행하며, 이전 기능 순서표는 확정 순서가 아니다. 수집 원장·중복 제거·ACK 책임을 다시 설계하거나 후속 기능을 곧바로 구현하지 않는다. 기존 개발 DB·볼륨 마이그레이션은 수행하지 않았다.

연결 검증은 위 작업의 입력·출력 계약에 붙인다. 수집의 ACK·commit, 귀속의 공개 보류, BFF의 두 DB 권한 전달, 배치의 확정 트랜잭션을 확인한다. 부하에서는 조회·배치 동시 실행, 적체 경고·복구와 품질 시나리오 수치를 측정한다. 단위 테스트만으로 전체 기능 완료를 선언하지 않는다.

## 4. 미결 사항

| 판단 | 필요한 이유 |
|---|---|
| 60초 사용 구간의 조회·월·가격 경계 처리 | 이벤트는 점유 시작 기준, API는 UTC 분 경계·월간 정산은 UTC 월이다. 완전 포함 조건만 쓰면 걸친 구간이 누락될 수 있다. 분할·귀속 정책은 아직 선택하지 않았다. |
| 수집의 운영 검증 | 구현·로컬 장애 검증과 전원 장애·디스크 영구 손실·장기 보관·대규모 성능 검증을 구분한다. 운영 TLS·비밀 관리·외부 알림도 후속 작업이다. |
| 점유 사실 입력·귀속 공개 계약 | 외부는 내부 반영을 기다리지 않고 재할당할 수 있다. 점유 사실이 사용량보다 늦을 때도 필요한 이력의 반영을 확인해야 한다. 캐시·DB 재조회만으로 미도착 사실을 배제할 수 없다. |
| 점유 이력·귀속·캐시의 최소 실행/저장 구조 | 내부는 수신 이후 멱등 반영·버전 비교·공개 경합·재시작을 방어한다. Kafka 기록 전 사실 보존은 외부 계약이며 VM 제어는 구현하지 않는다. |
| 귀속 모델과 이력 정정 | 원시 데이터는 BFF에 노출하지 않는다. 재귀속 시 이중 공개를 막는 물리 모델이 필요하다. |
| 회사 불명 귀속 오류의 정산 차단 범위 | 해결 전 확정 금지는 유지하되 어느 회사·월 작업을 막을지 정해야 한다. |
| 지연 목표의 측정 구간 | 품질 시나리오의 정상 반영 10초·1분과 부하 중 허용 5분을 각각 어느 구간에서 측정할지 명시해야 한다. 수치는 임의로 완화하지 않는다. |

인증은 현재 서버 세션이다. JWT·캐시 제품·선집계·추가 실행 단위는 새 승인 없이 도입하지 않는다.

## 6. 새 세션 인계 프롬프트

> docs/implementation-roadmap.md와 docs/implementation-status.md, 적용되는 AGENTS.md를 읽어줘. VM 제어·요청 만료·재할당 승인은 외부 책임이고 내부는 확정된 점유 사실을 이력에 반영해. 점유 이력(캐시 포함)·사용량 귀속 모듈 후보의 불변식은 logical-data-model.md를 따라. 다음은 점유 사실보다 사용량이 먼저 도착하는 경우의 공개 안전성 계약이야. 계약 확인 후 실행 위치·데이터 모델·순서를 정하고, 외부 재할당을 내부 캐시가 차단한다고 가정하지 마. 작업별 기존 근거는 상태표에 있으며 점유 이력·BFF 업무·배치는 미구현이야. 수집 CI 통과를 전원 장애·보관 만료·성능·운영 보안 검증으로 확대하지 마. 새 컨테이너나 후속 구현 승인을 가정하지 말고 학습·승인 후 TDD로 구현해. 수집 ACK·원장 설계는 반복하지 마. 작업 단위별 커밋 후 최종 푸시해.
