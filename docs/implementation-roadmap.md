# Implementation Roadmap

## 1. 원칙

- 문서 영역을 한 번에 모두 구현하지 않고, 실행 가능한 수직 기능을 차례로 완성한다.
- 각 단계는 작은 정확성 테스트를 먼저 통과하고 다음 단계로 간다.
- 선집계·Redis·추가 서비스는 측정 결과가 요구할 때만 도입한다.

## 2. 단계

| 단계 | 결과물 | 완료 기준 |
|---|---|---|
| 0. 설계 기반 | 요구사항·계약·ADR·물리 모델 | DB 스키마와 대표 쿼리 실행 통과 |
| 1. 실행 기반 | Java 21 빌드, 로컬 PostgreSQL·Kafka·ClickHouse | 모든 프로세스 기동과 스키마 자동 적용 |
| 2. 수집 파이프라인 | 발생기 → 수신 API → Kafka → 원장 적재기 → ClickHouse | 중복·재시작 포함 유실 0건 |
| 3. 인증·권한 | 세션 로그인, 소속·역할, RLS, 감사 | 테넌트 노출·무권한 처리 0건 |
| 4. 비용 조회 | 비용 탐색·원본 커서·확정 조회 API | 계약 테스트와 작은 데이터 정확성 통과 |
| 5. 월간 정산 | 회사·월 작업, 재시도, 검증·확정 | 중단 후 재실행 차이 0원 |
| 6. 웹 화면 | 예상·확정 금액, 근거, 권한 관리 | Viewer·Admin 핵심 흐름 시연 가능 |
| 7. 성능·장애 | k6 부하, 적체·DB 장애 실험, 측정 보고서 | QS-01~QS-13 결과와 병목 근거 기록 |

## 3. 구현 단위

```text
usage-event-api       : 인증·검증 후 Kafka 기록
usage-ledger-writer   : Kafka 소비 후 ClickHouse 원장 적재
settlement-batch      : 월간 검증·재시도·확정
billing-bff           : 세션·RBAC·비용·정산 API
billing-web           : 대시보드
usage-generator       : 정상·중복·지연·부하 이벤트 발생
```

공통 코드는 이벤트 계약과 계산 값 타입처럼 실제 공유가 필요한 범위로 제한한다.

## 4. 다음 작업

단계 1의 빌드 구조와 로컬 인프라를 만든 뒤, 빈 애플리케이션이 아니라 이벤트 하나가 ClickHouse 원장까지 도달하는 단계 2의 최소 흐름을 바로 구현한다.
