# BFF 고객 조회·접근 통제 LLD

## 1. 상태·범위

**① 책임·경계, ② 인터페이스 계약, ③ 입력·상태 공간과 오라클 설계 완료:** [테스트 설계](bff-access-test-design.md)의 검증 목적 36개에 승인한 G1–G6 기대 동작을 반영하고 API 계약을 동기화했다. 다음은 ④ 내부 구성요소 책임·협력이다. BFF 업무 구현·실제 보안 검증은 아직 없다.

C2의 **BFF · 인증/인가 컨테이너**에서 고객 조회 경로를 구체화한다. 귀속 재계산·가격 계산·월간 정산은 제외한다. BFF는 워커·배치를 동기 호출하지 않고 저장소를 읽는다.

```text
요청 → [ BFF ]
        인증 → 확인된 사용자 신원
          ↓
        인가 → 허용된 행위·회사 범위
          ↓
        공개 가능성 → 공개 가능한 결과
          ├ PostgreSQL: 승인·차단·점유 이력 근거
          └ ClickHouse: 승인 개정의 귀속 결과
```

인증·인가에서도 PostgreSQL의 세션·현재 소속·역할을 읽는다. DB 접근 자체가 공개 가능성 책임에만 속하는 것은 아니다.

## 2. 책임·인터페이스 계약

| 책임 | 입력 | 성공 시 보장 | 거부·장애 |
|---|---|---|---|
| 인증 | 세션 쿠키 | 서버가 검증한 사용자 식별자 | 세션 없음·만료·무효는 `401`, 인증 저장소 장애는 `503`. 후속 처리 차단 |
| 인가 | 확인된 사용자 식별자 + 서버가 정한 요청 행위 | 현재 소속·역할로 허용된 행위와 회사 범위(`TenantScope`) | 유효 소속 없음·역할 부족은 `403`, 권한 저장소 장애는 `503`. 후속 조회 차단 |
| 공개 가능성 | 허용된 회사 범위 + 조회 조건 | 공개 판단 확정 시 해당 회사의 승인 개정이며, 관련 차단이 없고 현재 이력 근거와 저장 결과가 유효함 | 보류와 저장소 장애는 내부에서 구분하되 대외 `503 / SERVICE_UNAVAILABLE`. 부분 행·총계·비공개 원인을 반환하지 않음 |

- **인증:** [ADR-005](adr/0005-authentication-state-management.md)의 서버 세션·Spring Session JDBC를 유지한다. Spring Security 결과를 요청 진입부에서 받아 사용자 식별자를 명시적으로 전달한다. 별도 인증 인터페이스를 새로 만들지 않는다.
- **인가:** [ADR-006](adr/0006-tenant-rbac-enforcement.md)의 Method Security를 채택한다. 회사·역할은 서버의 현재 데이터로 확인하며, 클라이언트가 보낸 신원·회사·역할을 권한 근거로 사용하지 않는다.
- **공개 가능성:** PostgreSQL의 귀속 승인 개정·귀속 오류·관련 점유 이력을 확인하고 ClickHouse에서 정확히 그 개정의 결과를 읽는다. BFF는 승인 사실을 만들지 않는다. 월간 확정 조회는 별도로 배치가 기록한 확정 상태를 확인하며, 배치 실패를 모든 사용량의 공개 차단으로 확대하지 않는다.

세 책임은 계약 구분이며 Java `interface` 세 개를 만들라는 결정이 아니다. 기존 [API 계약](api-contract.md)의 로그인·로그아웃 경로와 타사 리소스 존재 비노출 원칙을 유지한다.

## 3. 테스트 설계 원칙

```text
계약 → 입력·상태·환경 분리 → 처리 영역·경계·조건 조합
 → 상태 전이·경합·장애 → 오라클 → 필요한 최소 실행 범위
```

- 응답이 같아도 검증 경로가 다르면 별도 사례를 둔다. 쿠키 없음과 서버에서 폐기된 세션은 모두 `401`이어도 같은 검사로 대체하지 않는다.
- 순서가 있는 값은 경계 직전·정확한 경계·직후를 검사한다. 만료는 승인한 비활동 30분 정책을 기준으로 하며 시간 간격은 실제 저장 정밀도에 맞춘다.
- 조건 조합은 실제 가능한 조합과 판단 순서를 반영한다. 저장소 조회 실패는 세션 유효·만료를 알 수 없는 상태이며, 거부와 장애를 구분한다.
- 상태 자체와 상태를 바꾸는 동작을 각각 검사한다. 로그아웃은 브라우저 쿠키 삭제만이 아니라 서버 세션의 효력 제거를 검증한다.
- 오라클은 응답뿐 아니라 금지된 후속 처리·정보 노출도 관측한다. 잘못된 구현도 통과할 수 있는지 반례를 찾는다.
- 로그아웃 검증은 같은 쿠키로 보호 요청 성공 → 로그아웃 → 옛 쿠키로 `401`을 비교한다. 처음부터 모든 요청을 거부하는 구현을 배제한다. 실제 인증 필터·세션 저장소를 연결하되 이 서버 보장에 브라우저까지 요구하지 않는다.

개별 검증 목적·오라클·최소 실행 범위는 [테스트 설계](bff-access-test-design.md)를 따른다. 세션 검증·인가·공개 판단의 기준점을 나누고 각 시점의 선후관계를 고정해 검사한다.

## 4. 후속 설계·작업 순서

G1–G6 정책과 OpenAPI 오류 선언은 반영했다. 이제 구성요소와 객체 관계가 이 기대 동작을 어떻게 보장할지 정한다.

- 레이어 해부 → 구성요소 책임·인터페이스 → 객체의 협력·의존 관계로 진행한다.
- 공개 보호는 관련 VM의 PG 잠금 아래 CH를 읽는 방식을 후보로 검증한다. 연결 반환 계약의 예외·잠금 호환성·조회 범위 누락·VM 잠금 순서·제한시간·BFF 최소 권한은 아직 결정하지 않았다.
- 실제 프레임워크의 만료·폐기·인가 시점과 고객 DB 신원 선택을 위 오라클에 연결한다. 워커 내부 검증을 고객 격리 완료로 간주하지 않는다.

```text
① 책임·경계 ✓ → ② 인터페이스 계약 ✓
 → ③ 입력·상태 공간 + 오라클·테스트 범위 ✓
 → ④ 내부 구성요소 책임·협력 → ⑤ 객체 수준 패턴
 → ⑥ 구현 계획·최종 검토 → 승인 후 TDD
```

사용자와 개념·관계부터 단계별로 이해를 맞춘다. 사용자 감독 범위는 C3까지이며, 파일·메서드 수준 표현은 에이전트가 담당한다.
