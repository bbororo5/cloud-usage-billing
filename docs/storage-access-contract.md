# Storage Access Contract

> 상태: 승인 — ADR-006 및 ADR-008 반영. BFF의 원시 원장 접근 차단, ClickHouse 테넌트별 신원/Row Policy, 점유 이력 귀속 및 정산 계약을 정의한다.

## 1. 목적

PostgreSQL·Kafka·ClickHouse 사이에서 데이터가 언제 안전하게 기록되고, 어떤 범위와 규칙으로 읽히는지 정의한다.

## 2. 사용자 요청

```text
세션 user_id 확인
→ PostgreSQL 트랜잭션에서 user_id SET LOCAL
→ 본인 활성 소속 조회
→ billing_account_id SET LOCAL
→ 현재 역할 확인과 RLS 적용 조회
→ PostgreSQL 트랜잭션 종료
→ 테넌트별 DB 신원 및 Row Policy로 ClickHouse 귀속 조회 모델 조회
```

- PostgreSQL 커넥션은 종료 전에 반환하지 않는다.
- ClickHouse 호출 전에 PostgreSQL 커넥션을 반환해 두 저장소를 동시에 점유하지 않는다.
- BFF는 ClickHouse 테넌트별 읽기 신원과 Row Policy로 자기 회사 데이터만 허용되는 귀속 조회 모델을 읽는다.
- BFF 계정은 ClickHouse 원시 원장(`usage_record_delivery`)에 대한 접근 권한을 갖지 않는다.

## 3. 이벤트 적재

```text
발생기가 브로커 인증 후 source를 key로 직접 발행
→ Kafka 내구성 ACK (입력 내용은 발생기 계약으로 신뢰)
→ 이벤트를 3행으로 변환해 ClickHouse 적재
→ 해당 묶음의 데이터·파일 메타데이터 디스크 동기화 완료
→ Kafka offset commit
```

- 재시작·재시도로 같은 전달이 다시 적재될 수 있다.
- 저장 완료 기준은 적재 묶음의 디스크 동기화 완료다. 쓰기 성공 응답이나 OS 메모리 반영만으로 offset을 진행하지 않는다. 동기화·적재 실패 시 해당 묶음의 offset을 확정하지 않는다.
- 기준은 승인됐지만 직접 소비의 실제 동기화 설정·offset 진행 순서는 구현 전 검증한다. 모든 적재 대상에 적용하며 중간 비동기 경로가 보장을 끊지 않아야 한다. [ClickHouse 내구성 설명](https://clickhouse.com/docs/reference/engines/table-engines/integrations/kafka#data-durability)
- 디스크 동기화 대기로 인한 처리량·지연을 측정한다. 디스크 자체의 영구 손실은 이 기준만으로 보호하지 못하며 별도 복구 범위로 구분한다.
- 별도 내용·출처 검증과 자동 오류 격리는 두지 않는다. 파싱·적재가 불가능하면 실패로 남기고 해당 소비 위치를 건너뛰지 않는다. 원인 해소 후 재처리한다.
- 원시 원장은 회사 정보 없이 VM `source`와 Kafka topic·partition·offset을 보존하고, 귀속 및 집계는 논리 키별 전달 사본을 하나로 취급한다.
- 동일 논리 키의 내용은 발생기가 유지한다. 내용 충돌 검사는 현재 수집 범위에서 제외한다.
- ClickHouse 실패 중에는 offset을 진행하지 않아 Kafka에서 복구한다.

### 중단·복구 정책

- 재시작은 같은 consumer group의 파티션별 committed offset에서 재개한다. ClickHouse의 마지막 행으로 소비 위치를 추측하지 않는다. commit 응답 유실 시에도 Kafka에 실제 기록된 위치를 기준으로 한다.
- 디스크 동기화 전 중단은 다시 적재한다. 동기화 후 commit 전 중단은 이미 저장된 행이 재전달될 수 있으므로 중복 반영을 막는다. commit 후에는 확정 위치에서 이후 이벤트를 처리한다.
- 일시 장애는 간격을 두고 자동 재시도한다. 지속 실패는 담당자에게 알리며 재시도 횟수 소진을 이유로 이벤트를 폐기하거나 실패 구간을 건너뛰지 않는다. 원인 해소 후 재개한다.
- 복구는 Kafka에 재처리할 이벤트와 소비 위치가 보존된 범위에서 가능하다. 장기 적체는 보관 만료 전에 경고·대응한다. 보관·용량, 재시도 간격, 지속 실패·적체 알림 기준은 구현 전 정한다.

자동 오류 격리가 없으므로 계약 위반 입력은 원인을 해결할 때까지 소비를 막을 수 있다. 이 정책의 자동 재시도·알림이 실제 동작하는지는 내장 소비 경로 검증에 포함한다.

## 4. 점유 이력 조회와 캐시 갱신

PostgreSQL이 점유 이력 원본을 소유한다. 귀속 처리는 반복 조회를 줄이기 위해 점유 이력 캐시를 사용하고, 필요한 과거 구간이 없으면 PostgreSQL에서 조회한다. ClickHouse에 점유 이력 사본을 동기화하는 방식은 채택하지 않는다.

- 점유 시작·종료는 내부 자원 할당 측의 별도 사건이다. 시작은 유휴 VM에 회사 이력을 추가하고, 종료는 해당 이력에 실제 해제 시각을 기록한다. 과거 이력은 삭제하지 않는다.
- 점유 제어 메시지는 사용량과 별도 Kafka 토픽에 VM source를 key로 내구성 있게 기록한다. PostgreSQL 이력·VM별 증가 버전 및 캐시에 재처리 가능하게 반영한다. 양쪽 반영과 처리 결과의 내구 기록이 완료된 뒤 offset을 commit한다. 중간 실패는 재전달로 복구하며 원장·캐시 갱신은 멱등하게 처리한다.
- 같은 변경 사건의 재전달은 점유 이력을 중복 생성하지 않는다. 역순 사건은 현재 상태를 되돌리지 않으며 누락된 선행 사건은 복구 대상으로 남긴다.
- 종료 효력 시각은 캐시 ACK 시각과 구분한다. 캐시 실패로 이전 회사의 점유·과금을 연장하지 않으며, 안전한 반영 확인 전 신규 재할당과 영향 구간 공개를 보류한다.
- 캐시는 버전을 비교해 오래된 조회·갱신 결과가 최신 이력을 덮어쓰지 못하게 한다. 이는 캐시 갱신 거부이며 사용량 이벤트 폐기가 아니다.
- 변경 시작부터 캐시 반영 확인까지 해당 VM의 변경 시점 이후 사용량 귀속·공개를 보류한다. DB 반영 후 캐시 갱신 실패 시에도 보류를 유지하고 재시도한다. 영향 없는 이전 구간과 다른 VM의 처리는 계속한다.
- 이미 이력을 읽은 처리도 공개 시 위 조건을 만족해야 한다. TTL이나 캐시 갱신 ACK만으로 안전성을 판단하지 않는다.
- 늦게 도착한 사용량은 도착 시각이 아닌 사용 구간의 회사에 귀속한다. 과거 이력이 캐시에 없으면 원장을 읽으며, 캐시 누락을 미귀속으로 단정하지 않는다.

캐시 저장 기술, 버전 비교의 원자적 적용, 여러 귀속 프로세스의 공개 보류 및 재시작 복구 방식은 구현 전 설계·검증한다. 과거 이력 정정 시 이미 공개된 결과의 재귀속 절차도 후속 설계 대상이다.

### 점유 요청 기한과 완료 조건

요청 기한은 접수 후 최대 60초이며 메시지 재시도로 연장하지 않는다. Kafka 보관 기간과 별개인 업무 처리 기한이다. 점유 시작 요청은 실행 의도이며 실제 점유 시작 사실과 구분한다.

| 흐름 | 확정 동작 |
|---|---|
| 점유 시작 | 요청을 Kafka에 기록 → 원장·캐시 준비 → 기한과 유휴 상태 확인 → 독점 확보 활성화·시작 시각 기록 → 완료. 준비 중에는 사용·과금하지 않는다. |
| 시작 기한 만료 | 활성화되지 않은 요청을 만료로 확정하고 준비 상태를 정리한다. 이후 재전달돼도 활성화하지 않는다. |
| 점유 종료 | 실제 해제 시각에 측정을 종료하고 종료 사실을 Kafka로 전달 → 원장·캐시 반영 → 완료. 요청 시간이 지나도 종료 반영은 계속한다. |
| 완료 응답 유실 | 동일 요청 ID로 기존 결과를 확인한다. 이미 활성화된 점유를 새로 만들거나 시간 초과만으로 취소하지 않는다. |

- 시작 활성화와 만료는 하나의 요청에서 동시에 성립할 수 없다. 최종 결과를 내구 기록하고 재처리 시 재사용한다.
- 제어 메시지는 사건/요청 ID, VM source, 대상 점유 이력 ID, 종류 및 관련 시각을 식별할 수 있어야 한다. 시작 요청은 고정 만료 시각을, 종료 사실은 실제 해제 시각을 갖는다. 이전 점유의 지연 종료가 새 점유를 종료시키면 안 된다.
- 종료 사실은 Kafka ACK까지 잃지 않고 재전달할 수 있어야 한다. 실제 해제 후 Kafka 기록 전 장애의 복구 방식은 내부 할당 시뮬레이션 구현 시 검증한다.
- 만료된 시작 요청은 명시적인 만료 결과를 남긴 뒤 소비를 완료한다. 이미 발생한 종료 및 사용량 이벤트에는 시작 요청의 만료 정책을 적용하지 않는다.
- 시작 활성화의 원자적 판정과 캐시 공개 제어는 구현 설계 대상이다. 캐시 준비만으로 점유가 활성화되었다고 판단하지 않는다.

## 5. 가격 동기화

PostgreSQL `clickhouse_price_rate_export`가 가격 사본의 유일한 입력이다.

```text
PostgreSQL 가격 export 읽기
→ ClickHouse price_rate_snapshot batch insert
→ 최신 sync_version과 행 수 검증
→ 계산 가능 상태로 공개
```

- MVP에는 가격 변경 API가 없으므로 배포 시 동기화하고 서비스 시작 전에 검증한다.
- 새 가격 버전은 적용 시각 전에 같은 명령으로 동기화한다.
- 반복 동기화는 같은 `sync_version`을 써도 안전하다.
- 사본 누락·중복 가격은 0원으로 숨기지 않고 API 503 또는 배치 실패로 처리한다.

## 6. 비용·원본 조회

- 비용은 귀속 조회 모델에서 회사·기간으로 범위를 제한하고 중복 제거 → 가격 조인 → 그룹화 순서로 계산한다.
- 현재 API 계약은 분 경계의 `[from, to)` 안에 완전히 포함된 사용 구간을 계산한다. 점유 기준 60초 구간이 조회·월·가격 경계를 걸치는 경우의 정책은 미결이다. 확정 전 임의 분할하거나 누락시키지 않는다.
- 금액은 ClickHouse에서 scale 18로 계산하고 PostgreSQL 확정 시 scale 6으로 반올림한다.
- `dataAsOf`는 선택된 논리 레코드의 최대 `charge_period_end`이며 해당 시각까지의 수집 완전성을 보증하지 않는다.
- 원본 첫 페이지는 `snapshot_ingested_at`을 정하고 후속 커서에 서명해 포함한다.
- 커서 정렬 키는 `charge_period_end + source + id + meter`다.

대표 비용 쿼리는 귀속 조회 모델의 물리 형태를 단계 3에서 확정한 뒤 [`database/clickhouse/queries`](../database/clickhouse/queries)에 추가한다. 실제 API의 동적 필터·그룹은 허용 목록으로 조립하고 값은 바인딩한다.

## 7. 월간 확정

1. Kafka 적체와 ClickHouse 적재 지연이 0인지 확인한다.
2. 회사·월 작업을 잠그고 새 실행 시도를 만든다.
3. 대상 월에 미해결 미귀속(`AttributionError`) 또는 중복 점유 사용량이 0건인지 검증한다. (존재 시 확정 차단)
4. 현재 예상 총액을 기록한 뒤 같은 닫힌 월을 다시 계산한다.
5. 데이터 이상 0건, 가격 동기화 일치, 두 금액 차이 0원을 검증한다.
6. PostgreSQL 한 트랜잭션에서 검증·확정 결과를 만들고 작업을 종료한다.

재시도는 새 `run_id`를 사용하며 완료된 시도와 기존 확정 결과를 덮어쓰지 않는다.

## 8. 실패 기준

| 상황 | 동작 |
|---|---|
| Kafka 기록 실패 | 수신 성공으로 응답하지 않는다. |
| ClickHouse 적재 실패 | offset을 commit하지 않고 재시도한다. |
| 미귀속·중복 점유 탐지 | 원본을 보존하고 해당 사용량을 오류로 격리한다. 해결 전 공개 및 관련 월간 확정을 차단한다. |
| BFF의 원시 원장 접근 시도 | 저장소 및 애플리케이션 레벨에서 즉시 차단한다. |
| 가격 누락 | 해당 비용 응답과 월 확정을 실패시킨다. |
| 가격 사본 지연 | 마지막 사본으로 조용히 계산하지 않고 버전 검증에 실패한다. |
| PostgreSQL 권한 확인 실패 | 기본 차단한다. |
| 배치 중단 | 시도를 실패로 남기고 새 시도로 재실행한다. |

귀속 오류에는 원본 식별자·VM source·사용 구간·실패 사유를 기록한다. 개발자·운영 담당자에게 같은 원인의 반복 오류를 묶어 알리고, 필요 시 PM에게 미과금 현황을 공유한다. 점유 이력 수정 후 원본을 재처리하며, 해결 이력을 남긴다. 다른 VM의 수집은 계속한다. 알림 채널과 반복 오류 묶음 기준은 구현 시 정한다.
