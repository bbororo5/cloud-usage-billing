# Architecture Test Plan

## 1. 목적

아키텍처 드라이버가 구현 과정에서 훼손되지 않도록 검증 방법과 실행 시점을 미리 정한다.

## 2. 테스트 계획

| 대상 | 검증 내용 | 통과 기준 | 실행 시점 |
|---|---|---|---|
| DR-01 정확성 | 중복, 지연, 순서 변경 이벤트를 처리하고 배치 결과와 비교 | 중복 반영 0건, 금액 차이 0원 | 매 커밋 |
| DR-02 지속 처리 | 정상 초당 330건과 최대 초당 1,000건을 입력 | 유실 0건, 99%가 10초 이내 반영 | 주요 변경 후 |
| DR-03 빠른 조회 | 이벤트 1억 건에서 사용자 500명이 동시에 조회 | p95 1초 이하, 데이터 지연 5분 이하 | 성능 검증 시 |
| DR-04 안전한 재처리 | 스트리밍과 배치를 처리 도중 중단한 후 재실행 | 중복 결과 0건, 정상 실행과 차이 0원 | 매 커밋·주요 변경 후 |
| DR-05 회사별 분리 | 다른 회사의 사용량, 집계, 캐시 결과에 접근 | 노출 데이터 0건 | 매 커밋 |
| 구조 유지 | 정해진 모듈 책임과 의존 관계를 검사 | 금지된 의존 관계 0건 | 매 커밋 |

## 3. 실행 단계

### 빠른 테스트

- 작은 데이터로 정확성, 재처리, 회사별 분리를 검증한다.
- 모든 커밋에서 실행한다.

### 통합 테스트

- 실제 데이터 흐름을 연결해 실패와 복구를 검증한다.
- 주요 기능이나 저장 구조가 변경될 때 실행한다.

### 성능 테스트

- 이벤트 처리량, 동시 조회, 대용량 데이터 성능을 검증한다.
- 개발 완료를 막지 않도록 별도로 실행하고 결과를 기록한다.

## 4. 준비 시점

1. 이벤트 형식을 정하면 테스트 이벤트와 발생기를 준비한다.
2. 모듈 책임을 정하면 구조 테스트를 준비한다.
3. API 계약을 정하면 부하 테스트 스크립트를 준비한다.
4. 스트리밍과 배치를 구현하기 전에 중복·실패·재실행 테스트를 먼저 작성한다.

아키텍처 결정에는 관련 테스트와 통과 기준을 함께 기록한다.
