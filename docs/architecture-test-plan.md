# Architecture Test Plan

HLD에서 경계·계약 가드레일을 마련하고, 흐름별 LLD에서 입력·상태공간과 오라클을 설계한 뒤 TDD로 구현한다.

아래 테스트는 목표이며 통과 기록이 아니다. 기존 수집 검증 결과를 ClickHouse 직접 소비 구조의 검증으로 간주하지 않는다.

## 운영

| 구분 | 범위 |
|---|---|
| 빠른 테스트 | 작은 데이터로 정확성·재처리·회사 분리·점유 귀속·역할 권한을 매 커밋 검증 |
| 통합 테스트 | 실제 데이터 흐름의 실패·복구·미귀속 차단을 주요 변경 후 검증 |
| 성능 테스트 | 처리량·동시 조회·대용량 성능을 별도로 실행하고 기록 |

### 성능 개선 기록

- 조건: 버전·자원·데이터 규모·중복 비율·요청 부하를 명시하고 비교 시 유지한다.
- 근거: 실행 계획, 읽은 행·바이트, 메모리, p95 및 적재 지연으로 병목을 찾고 관련 엔진 동작과 연결해 설명한다.
- 검증: 한 가지 변경의 전후 수치를 비교하고 중복 반영·금액·격리 테스트도 다시 통과시킨다. 측정 전 선집계나 저장 구조 변경을 미리 확정하지 않는다.

## 준비 순서

1. 승인된 이벤트·API 계약의 정상/위반 예제와 CI 검사를 먼저 갖춘다.
2. 확정된 책임·접근 경계를 구조·권한 테스트로 연결한다. 미정인 모듈 구조는 검사로 고정하지 않는다.
3. 흐름별 내부·연결 LLD에서 입력·상태·장애 시점과 독립적인 판정 기준을 설계하고 승인받는다.
4. 구현할 동작의 실패 확인 → 최소 구현 → 리팩터링·통합·회귀 검증을 반복한다. 비용이 큰 부하·내구성 검증은 별도 수행한다.

모든 ADR에는 관련 테스트와 통과 기준을 함께 기록한다.

## PostgreSQL 접근 경계

기존 [접근 계약](storage-access-contract.md)과 [로컬 권한 설정](../database/postgresql/local-roles.sql)을 검사로 연결한다. 새 권한을 추가하는 결정이 아니다. **DB 계정의 작업 권한 → 회사별 행 격리 → 사용자의 역할 검사**를 구분한다.

### 허용·금지 작업

아래는 현재 테이블의 허용 목록이다. 표시하지 않은 작업은 금지하며, 허용된 쓰기도 상태·무결성 제약을 만족해야 한다.

| 데이터 | BFF (`billing_bff`) | 배치 (`billing_batch`) |
|---|---|---|
| 사용자 `app_user` | 조회 | 접근 금지 |
| 회사 `billing_account` | 조회 | 조회 |
| 소속 `billing_membership` | 조회·추가·변경·삭제 | 접근 금지 |
| 세션 `spring_session`, `spring_session_attributes` | 조회·추가·변경·삭제 | 접근 금지 |
| 감사 `security_audit_event` | 추가 | 접근 금지 |
| 가격 `clickhouse_price_rate_export` | 접근 금지 | 조회 |
| 정산 작업·시도 `settlement_job`, `settlement_attempt` | 접근 금지 | 조회·추가·변경 |
| 정산 검증 `settlement_validation` | 접근 금지 | 조회·추가 |
| 확정 금액 `monthly_settlement` | 조회 | 조회·추가 |

가격 원본 변경과 발생기 자격증명 조회는 양쪽 모두 금지한다. 두 계정은 테이블 소유자·superuser·BYPASSRLS가 아니어야 하며, 우회 가능한 역할 전환도 허용하지 않는다. 점유 모델 등 미구현 데이터의 권한은 해당 LLD에서 정한다.

### 테스트 설계

폐기 가능한 PostgreSQL에 관리 계정으로 두 회사의 정상 데이터를 준비한 뒤, **실제 BFF·배치 로그인 계정**으로 다음을 검사한다. 관리 계정의 성공을 앱 계정의 성공으로 간주하지 않는다.

| 경계 | 입력·상태 구분 | 판정 기준 |
|---|---|---|
| 작업 권한 | 두 계정 × 위 허용 목록/금지 작업 | 정상 작업은 성공하고 결과가 맞음. 권한 없는 작업은 `42501`로 거부되며 데이터 불변. 수정 불가능한 가격 뷰는 `55000` 거부와 쓰기 권한 부재를 따로 확인 |
| 회사 행 격리 | RLS 대상 × 자기 회사/다른 회사/회사 미설정 | 자기 회사만 조회·변경. 타사 조회·변경·삭제 대상은 0행, 타사 추가·회사 변경은 거부. 회사 미설정은 기본 차단 |
| 요청 간 격리 | 같은 연결에서 회사 A 트랜잭션 종료 후 문맥 없는 요청·회사 B 요청 | `SET LOCAL` 값이 남지 않으며 A 데이터 노출 0건 |
| 권한 우회 | 실제 계정의 속성·소유권·역할 상속/전환 경로 | 소유자·관리자·RLS 우회 권한 획득 불가 |

회사 미설정의 의도된 예외는 **인증된 `user_id`로 본인의 소속을 찾는 조회**다. 현재 RLS는 본인 소속 이력을 허용하므로 활성 여부는 BFF가 추가 확인한다. 사용자·세션 테이블에는 회사 RLS가 없으며 이 표의 회사 격리 검사를 일괄 적용하지 않는다.

DB는 BFF가 설정한 사용자·회사 문맥을 신뢰한다. 따라서 이 테스트만으로 위조 문맥이나 Viewer의 소속 변경을 막았다고 주장하지 않는다. **현재 소속 확인·Admin 검사·문맥 설정**은 BFF LLD의 실제 요청 테스트로 별도 방어한다. SQL 권한 거부와 무결성 제약 실패도 구분해 판정한다.

### 현재 범위

2026-09-18 실제 앱 계정에서 Admin 강등·월간 확정의 잠금 권한 충돌을 발견했다. 2026-09-20 검증 함수의 전용 소유자·제한된 권한을 적용해 **112건 모두 통과**했다. 앱의 직접 변경 권한·기존 잠금은 유지했다. 회사 격리·역할 전환·함수 재사용 차단도 검사한다. 실행법·범위·미검증 항목은 [접근 테스트 안내](../tests/postgres-access/README.md)를 따른다.

기존 `local_roles_test.sql`은 일부 권한 속성 조회, `schema_test.sql`은 별도 테스트 역할의 RLS·무결성 검사다. 이들의 통과를 실제 앱 계정의 정상 기능 성공으로 간주하지 않는다.

ClickHouse 접근 검사는 귀속 모델·테넌트별 신원 LLD 뒤에 구현한다. 코드 의존 검사는 아래의 승인된 모듈 경계만 대상으로 하며 미정인 패키지 구조는 고정하지 않는다.

## 모듈 의존 경계

`apps → apps`, `libs → apps`, 제품 코드의 `tests` 의존을 금지한다. Java `main`의 컴파일·실행·annotation processor 구성과 상속된 프로젝트 의존을 검사한다. 공용 모듈 사용과 테스트 코드의 제품 참조는 허용한다.

`./gradlew verifyModuleBoundaries :tests:module-boundaries:test --no-daemon`으로 실행한다. 무검사 기준선에서 위반·실행 연결 검사 9건 실패를 확인한 뒤, 구현 후 정상 사례 포함 13건을 통과했다. 실제 저장소 경계 검사도 통과했고 `check`·CI에 연결했다. 이는 코드 의존 검사이지 런타임 격리 증명이 아니다. 세부 범위는 [검사 안내](../tests/module-boundaries/README.md)를 따른다.
